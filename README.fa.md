## این چی هست

مجموعه‌ای از **دستورهایی که خودت عمداً صدا می‌زنی** — نه یک فایل قانون که در
پس‌زمینه کار کند، نه پلاگینی که شیوهٔ کدنویسی مدل را عوض کند. هر دستور یک
لحظه را پوشش می‌دهد که پروژه‌های AI-محور پیوسته در آن می‌لغزند: نیازمندی‌ای
که کسی قطعی‌اش نکرد، پلنی که کسی داوری‌اش نکرد، گزارش باگی که کسی نبستش.

هیچ‌چیز اینجا خودبه‌خود اجرا نمی‌شود. همهٔ اسکیل‌ها
`disable-model-invocation: true` دارند. یا `/plan-check` را می‌زنی، یا اصلاً
اتفاق نمی‌افتد.

### کدام ابزار، کدام لحظه

دستورها چهار لحظهٔ متفاوت را پوشش می‌دهند و فقط یکی‌شان خودکار است:

| لحظه | چه چیزی پوششش می‌دهد | کی صدایش می‌زند |
|---|---|---|
| **قبل از کد** — روی پلن | `/plan-check` | تو |
| **حین نوشتن** | نردبان در `CLAUDE.md` | همیشه فعال — و ضعیف‌ترین حلقه |
| **بلافاصله بعد** — روی دیف | ممیزی دامنهٔ `/explain` | تو |
| **هر چند هفته** — روی کدبیس | `/find-overengineering` | تو |

`/find-overengineering` یک جاروست، نه چک هر فیچر. رتبه‌بندی‌اش بر پایهٔ شمارش
در یک **تودهٔ کد** است، پس روی یک دیف ۴۰ خطی چیزی برای رتبه‌بندی ندارد و فقط
نویز تولید می‌کند. ابزار آن لحظه `/explain` است که هر فایل تغییرکرده را به
چیزی که خواستش برمی‌گرداند و هرکدام را که به هیچ‌چیز نرسد گزارش می‌کند.

## مشکل چیست

مشکل این نیست که Claude بد کد می‌زند. مشکل این است که **راهی ندارد بفهمد کارش
درست بوده یا نه**، و **نمی‌داند در این پروژه کارها چطور انجام می‌شوند**.

پس حدس می‌زند. پیوسته، باورپذیر، و هر سشن یک‌جور.

این جعبه‌ابزار سه چیز را حل می‌کند:

| مشکل | راه‌حل |
|---|---|
| «هر بار یه جور می‌زنه» | فایل‌های قانون که کانونشن‌های پروژه را نگه می‌دارند |
| «نمی‌فهمم کارش درست بوده یا نه» | هر کاری با یک چک قابل‌اجرا تمام می‌شود |
| «پیدا می‌کنه ولی درست نمی‌شه» | حلقهٔ اصلاح تکی |

و یک اصل که همه‌جا تکرار می‌شود:

> **پیش‌فرض را پایین بگیر.** بیشتر کارها به هیچ‌کدام از اینها احتیاج ندارند.

## شروع سریع

```bash
# ۱. داخل پروژه‌ات کلون کن، با اسم _toolkit
cd my-laravel-project
git clone https://github.com/abdian/claude-toolkit-laravel.git _toolkit

# ۲. شش ابزار پایه را نصب کن (پروژه‌ای)
bash _toolkit/install.sh          # ویندوز: powershell _toolkit\install.ps1

# ۳. اگر محصول را از صفر شروع می‌کنی، استارتر specs را بردار
cp -R _toolkit/specs ./specs

# ۴. Claude Code را از ریشهٔ پروژه باز کن
claude
```

بعد داخل Claude Code:

```
/skills          # تأیید کن لود شده‌اند
/start           # یک بار برای هر پروژه — Tier را تعیین می‌کند
```

> **دربارهٔ ریپوی تودرتو:** کلون کردن یک `.git` داخل `_toolkit/` جا می‌گذارد.
> یا `_toolkit/` را به `.gitignore` پروژه‌ات اضافه کن، یا تاریخچه‌اش را بریز
> دور و داخل پروژه نگهش دار:
> ```bash
> rm -rf _toolkit/.git      # حالا _toolkit/ با پروژه‌ات کامیت می‌شود
> ```
> گزینهٔ دوم پیش‌فرض بهتری است — اسکیل‌های نصب‌شده symlink به
> `_toolkit/skills/` هستند، پس هم‌تیمی‌ای که پروژه را کلون می‌کند آن‌ها را
> سالم تحویل می‌گیرد.

<details>
<summary><b>گزینه‌های نصب</b></summary>

```bash
bash install.sh                  # شش ابزار پایه، داخل همین پروژه
bash install.sh --all            # هر ۱۸ تا
bash install.sh --all --global   # به‌جایش در ~/.claude/skills
bash install.sh --all --copy     # کپی واقعی به‌جای symlink

```

معادل‌های PowerShell با سوییچ‌اند: `-All`، `-Global`، `-Copy`، `-Force`.

دامنهٔ پیش‌فرض **پروژه‌ای** است (`.claude/skills/`)، پس قابل کامیت است و هر
پروژه می‌تواند نسخهٔ خودش را داشته باشد. حالت پیش‌فرض **symlink** است؛ جایی که
symlink واقعی ممکن نباشد (ویندوز بدون Developer Mode) نصب‌کننده صریحاً می‌گوید
و کپی واقعی نصب می‌کند.

> ⚠️ یک skill شخصی (`~/.claude/skills/`) skill پروژه‌ای هم‌نام را **کنار
> می‌زند**. اگر قبلاً سراسری نصب کرده‌ای، نصب پروژه‌ای هیچ اثری ندارد.

## یک سند محصول داری. حالا چه کار کنی؟

این همان مسیری است که اکثر آدم‌ها با آن می‌رسند: یک فایل ورد پر از تصمیم، و
یک ریپوی خالی.

```
 سند-تو.docx
     │
     │  /spec-import سند-تو.docx
     ▼
 specs/*.md  ──────────►  گزارش شکاف‌ها — هرچه حدس زدنش را قبول نکرد
     │
     │  /clear، بعد فقط دربارهٔ شکاف‌ها مصاحبه کن
     ▼
 specs/ کامل  ──────────►  حالا کد می‌تواند شروع شود
```

مهم‌ترین بخش، فایل‌هایی نیست که پر می‌کند. **گزارش شکاف‌هاست.**

`/spec-import` فقط چیزی را می‌نویسد که سند صریحاً گفته. هر جای خالی، خالی
می‌ماند و گزارش می‌شود. پر کردن جای خالی با یک جواب باورپذیر بدترین حالت ممکن
است — هیچ‌وقت متوجه نمی‌شوی تصمیمی گرفته نشده، فقط پر شده، و شش ماه رویش کد
زده می‌شود.

`.docx` را `docx2md.py` همراه بسته تبدیل می‌کند — فقط کتابخانهٔ استاندارد
پایتون، بدون pandoc، بدون `pip install`. جدول‌ها را نگه می‌دارد، که مهم است،
چون `GLOSSARY` و `PERMISSIONS` و `PANELS` همه جدول‌اند.

**سند نداری؟** `specs/` را دستی پر کن — [`specs/HOWTO.md`](specs/HOWTO.md) یک
رودمپ هشت‌سشنه است، تقریباً یک بعدازظهر. ترتیبش **اجباری** است: زنجیرهٔ
وابستگی است، نه سلیقه.

| # | فایل | کی تصمیم می‌گیرد | زمان | هزینهٔ اشتباه |
|---|---|---|---|---|
| ۱ | `VISION.md` | **تو** | ۳۰–۴۵ د | کم |
| ۲ | `GLOSSARY.md` | **تو** | ۳۰ د | ⚠️ **بیشترین — اسم‌ها در جدول فریز می‌شوند** |
| ۳ | `PERMISSIONS.md` | **تو** | ۲۰–۳۰ د | متوسط |
| ۴ | `INTEGRATIONS.md` | **تو** + Claude | ۲۰ د | متوسط |
| ۵ | `FLOWS.md` · `PANELS.md` | Claude، از ۱–۴ | ۳۵ د | کم |
| ۶ | `contracts/*.yaml` | Claude | ۲۰ د | متوسط |
| ۷ | `BACKLOG.md` | تو | ۱۵ د | کم |

سه قانون حاکم بر این فاز:

۱. **تو تصمیم می‌گیری، Claude می‌نویسد.** فارسیِ شلخته حرف می‌زنی، او مرتب
   می‌کند. تصمیم هیچ‌وقت واگذار نمی‌شود.
۲. **یک فایل = یک سشن = یک `/clear`.**
۳. **جزئیاتِ زودتر از موعد = جزئیاتِ باطل.**

## هفت فاز — و اینکه هرکدام چقدر الزامی‌اند

<img src="assets/phases.png" alt="هفت فاز و وابستگی‌هایشان" width="100%">

**هیچ‌چیز اینجا جلویت را نمی‌گیرد.** هیچ اسکیلی از اجرا سر باز نمی‌زند، هیچ
هوکی کامیت را متوقف نمی‌کند. «الزامی» اینجا دو معنای کاملاً متفاوت دارد و قاطی
کردنشان همان چیزی است که گیج‌کننده‌اش می‌کند:

| نوع | یعنی چه |
|---|---|
| **وابستگی سخت** | اسکیل بدون ورودی‌اش واقعاً نمی‌تواند کارش را بکند. `/plan-check` بدون `BRIEF.md` چیزی برای داوری ندارد — فقط با پلن موافقت می‌کند. |
| **انضباط** | نادیده گرفتنش امروز چیزی را نمی‌شکند. بعداً با بهره از تو می‌گیرد. |

<details open>
<summary><b>۱ · IDEA — بدون ابزار</b></summary>

**چیه:** خودت، که تصمیم می‌گیری چیزی ارزش ساختن دارد.

**الزامی؟** چیزی برای اجرا نیست. اگر نتوانی در یک جمله بگویی برای کیست و بدونش
چه چیزی می‌لنگد، هیچ ابزاری پایین‌دست نجاتش نمی‌دهد.

</details>

<details>
<summary><b>۲ · SPECS — منبع حقیقت محصول</b></summary>

**چیه:** تصمیم‌هایی که کدبیس نمی‌تواند نگه دارد — این چیست، هر موجودیت چه
**نامیده** می‌شود، چه کسی اجازهٔ چه کاری دارد، وقتی درگاه پرداخت بالا نیست چه
اتفاقی می‌افتد.

**چطور استفاده می‌شود:**
```bash
cp -R _toolkit/specs ./specs
```
بعد یا `/spec-import سند-تو.docx` اگر سند داری، یا
[`specs/HOWTO.md`](specs/HOWTO.md) را قدم‌به‌قدم برو — هشت سشن، تقریباً یک
بعدازظهر.

**الزامی؟** **فقط Tier 3.** یک اسکریپت `GLOSSARY.md` نمی‌خواهد. ولی داخل
Tier 3، *ترتیب* یک وابستگی سخت است: `GLOSSARY.md` قبل از هر فایلی که اسم
موجودیت دارد — چون مایگریشنِ merge‌شده فریز است و اسم جدول غلط از خود پروژه
بیشتر عمر می‌کند.

**هزینه:** `/spec-import` ≈ ۱٬۸۰۰ توکن. تغییر نام یک جدول در ۴۰ فایل، شش ماه
بعد: به‌مراتب بیشتر.

</details>

<details>
<summary><b>۳ · BRIEF — «تمام شد» یعنی چه، کتبی</b></summary>

**چیه:** توضیح شلخته‌ات تبدیل می‌شود به ورودی، خروجی، **خارج از دامنه**، و یک
**شرط تمام شدن** که واقعاً قابل چک کردن باشد.

**چطور استفاده می‌شود:**
```
/brief
کد تخفیف به تسویه‌حساب اضافه کن
```
`/edges` همراه اختیاری‌اش است — فهرست می‌کند چه چیزی می‌تواند بشکند، با انتظار
اینکه اکثرشان عمداً نادیده بمانند.

**الزامی؟** برای هر چیزی که اسمش را فیچر می‌گذاری، بله — به‌عنوان انضباط.
ارزان‌ترین فاز کل مجموعه است و ورودی‌ای است که `/plan-check` لازم دارد.

بدون شرط تمام شدنِ کتبی، «تمام شد» یک احساس است. دو نفر دو احساس متفاوت
دارند، و سشن بعدی‌ات هم همین‌طور.

**هزینه:** ≈ ۹۵۰ توکن.

</details>

<details>
<summary><b>۴ · PLAN — ⭐ دروازه‌ای که خرجش را درمی‌آورد</b></summary>

**چیه:** داوری که پلن را در برابر `BRIEF.md` و قوانین سادگی می‌خواند و
**GO**، **TRIM**، یا **RETHINK** برمی‌گرداند.

**چطور استفاده می‌شود:**
```
[پلن را بگیر]  →  کپی کن  →  /clear  →  /plan-check  →  پیست کن
```

**الزامی؟** دو وابستگی سخت دارد و هر دو مهم‌اند:

- **`BRIEF.md` لازم دارد.** بدون چیزی برای داوری، فقط می‌تواند موافقت کند.
- **سشن تازه لازم دارد.** سشنی که پلن را نوشته فرض‌های خودش را به ارث برده —
  وکیل پلن است، نه قاضی‌اش. این همان قانونی است که آدم‌ها ردش می‌کنند، و
  ردش کردن کل فاز را به نمایش تبدیل می‌کند.

برای تغییر یک‌خطی کلاً فاز را رد کن. برای هر چیزی با بیش از حدود سه قدم، این
ارزان‌ترین لحظه‌ای است که over-engineering گرفته می‌شود — قبل از اینکه کدی
بشود که کسی بهش دل بسته.

**هزینه:** ≈ ۷۸۰ توکن. ارزان‌ترین اسکیل اینجا، نگهبان گران‌ترین اشتباه.

</details>

<details>
<summary><b>۵ · CODE — بخشی که همه از قبل دارند</b></summary>

**چیه:** خود کار. سهم جعبه‌ابزار، قوانینی است که ایجنت حین انجامش می‌خواند:
`templates/CLAUDE.laravel.md.template`، با یک نردبان سادگی هفت‌پله به زبان
لاراول.

**چطور استفاده می‌شود:** تمپلیت را به `CLAUDE.md` کپی کن و قلاب‌ها را پر کن.
`/lazy lite|full|ultra|off` شدت اعمال نردبان را عوض می‌کند و سطح را در
`CLAUDE.md` می‌نویسد، پس بین سشن‌ها می‌ماند.

**الزامی؟** خود کد که بله. نردبان انضباط است — و تنها جایی است که ابزارهای
دیگر با این یکی همپوشانی دارند.

**هزینه:** تمپلیت در هر پیام در کانتکست است، ≈ ۳٬۸۰۰ توکن، که بعد از اولین
درخواست کش می‌شود. خود `/lazy` ≈ ۶۳۰ توکن، فقط موقع صدا زدن.

</details>

<details>
<summary><b>۶ · AUDIT — دوره‌ای، نه برای هر فیچر</b></summary>

**چیه:** دو جاروی متفاوت که نباید با هم اجرا شوند. `/audit-codebase` دنبال باگ
و انحراف از کانونشن است → `AUDIT.md`. `/find-overengineering` دنبال پیچیدگی
اضافه → `COMPLEXITY.md`.

**چطور استفاده می‌شود:**
```
/audit-codebase app/Services    →  /clear  →  /find-overengineering app/Services
```
سشن‌های جدا، عمداً. سؤال‌های متضادی می‌پرسند و سشنی که هر دو جواب را نگه دارد
بد جواب می‌دهد.

**الزامی؟** نه — و اجرای هفتگی‌اش خودش یک علامت بد است. هر چند هفته، یا قبل از
ریلیز. Tier 1 هیچ‌وقت.

`/find-overengineering` یک **دستهٔ KEEP اجباری** دارد تا نتواند با اعلام
پیچیدگیِ همه‌چیز خودش را توجیه کند.

**هزینه:** ≈ ۱٬۳۰۰ و ≈ ۱٬۹۰۰ توکن.

</details>

<details>
<summary><b>۷ · FIX — یک finding، وگرنه گزارش می‌پوسد</b></summary>

**چیه:** حلقهٔ اصلاحی که دقیقاً یک finding شماره‌دار را درست می‌کند.

**چطور استفاده می‌شود:**
```
/clear  →  /fix-one AUDIT.md 3
```

**الزامی؟** **اگر ممیزی کردی، بله.** ممیزی بدون حلقهٔ اصلاح یعنی فایلی که
طولانی‌تر و ناراست‌تر می‌شود تا یک نفر پاکش کند. این همان شکستی است که این فاز
برایش ساخته شده.

یک **وابستگی سخت**: گزارش **و شماره** لازم دارد. `/fix-one` یعنی «finding
شمارهٔ ۳ را درست کن»، نه «باگ را درست کن» — و همین دقت است که دیف را به‌اندازهٔ
قابل‌بازبینی نگه می‌دارد.

شش قدم اجباری دارد، و قدم ۵ همان است که کارش را می‌سازد: `git diff --stat` باید
فقط فایل باگ‌دار، تستش، و فایل‌هایی که گزارش نام برده را نشان دهد. هر چیز
دیگری drift است و برگردانده می‌شود.

**هزینه:** ≈ ۹۵۰ توکن برای هر finding.

</details>

### این چقدر توکن خرجت می‌کند

اندازه‌گیری‌شده روی همین ریپو، نه تخمینی:

| | توکن | کِی |
|---|---|---|
| توضیح هر ۱۸ اسکیل | **≈ ۷۸۰** | هر پیام، کش‌شده |
| تمپلیت `CLAUDE.laravel.md` | ≈ ۳٬۸۰۰ | هر پیام، کش‌شده |
| بدنهٔ یک اسکیل | ۶۳۰ تا ۱٬۹۰۰ | فقط وقتی صدایش بزنی |
| بدنهٔ هر ۱۸ تا با هم | ≈ ۱۸٬۴۰۰ | در عمل هیچ‌وقت |

اجرای یک فاز **زیر ۲٬۰۰۰ توکن** خرج دارد. اشتباهی که برای جلوگیری‌اش هست —
فیچری که روی تصمیمی ساخته شده که کسی نگرفته، بعد دوباره خوانده و سرش بحث شده و
برگردانده شده — یک مرتبه بزرگ‌تر. عدد اول اندازه‌گیری شده؛ دومی تخمین است، ولی
نزدیک هم نیستند.

اسکیل‌ها بخش ارزانش‌اند. چیزی که واقعاً توکن می‌خورد سشن طولانی‌ای است که drift
کرده — دقیقاً همان که `/clear` بین فازها برای جلوگیری‌اش هست.

## هجده اسکیل

همهٔ اسکیل‌ها `disable-model-invocation: true` دارند — **فقط وقتی تو بخواهی**
اجرا می‌شوند، نه به تشخیص مدل.

### در ورودی

| دستور | کار |
|---|---|
| `/start` | ۲–۳ سؤال می‌پرسد، **Tier** تعیین می‌کند، فقط همان‌قدر ساختار می‌سازد |
| `/next` | وضعیت را می‌خواند و **یک** کار بعدی می‌گوید. نه لیست، نه رودمپ |

Tier برای این است که پروژهٔ کوچک، تشریفات پروژهٔ بزرگ نگیرد:

| Tier | کِی | چه راه می‌اندازد |
|---|---|---|
| ۱ — سبک | یک‌بارمصرف، زیر ~۱۵ فایل | **هیچی.** یک بریف و یک تست واقعی |
| ۲ — متوسط | چند هفته، ~۱۵–۶۰ فایل | `CLAUDE.md` حداکثر ۲۰ خط |
| ۳ — کامل | بلندمدت، بالای ۶۰ فایل | `ctx-*` کامل، rules، حلقهٔ ممیزی |

### قبل از کد

| دستور | کار |
|---|---|
| `/spec-import <سند>` | سند brain-dump را در `specs/` پخش می‌کند. شکاف گزارش می‌دهد، حدس نمی‌زند |
| `/brief` | توضیح شلخته → `BRIEF.md` با ورودی، خروجی، **خارج از دامنه**، **شرط تمام شدن** |
| `/edges` | حالت‌های مرزی را قبل از کد فهرست می‌کند — با انتظار اینکه اکثرشان عمداً نادیده بمانند |
| `/plan-check` | ⭐ پلن را در برابر بریف داوری می‌کند. حکم: **GO / TRIM / RETHINK** |

> `/plan-check` باید در سشن **تازه** اجرا شود. سشنی که پلن را نوشته سوگیری خودش
> را به ارث برده — وکیل پلن است، نه قاضی‌اش.

### بعد از کد

| دستور | کار |
|---|---|
| `/audit-codebase [مسیر]` | باگ، کد مرده، انحراف از کانونشن → `AUDIT.md` |
| `/find-overengineering [مسیر]` | پیچیدگی اضافه → `COMPLEXITY.md`، با دستهٔ اجباری KEEP |
| `/debt [مسیر]` | مارکرهای `lazy:` را در `DEBT.md` رتبه‌بندی‌شده جمع می‌کند |
| `/lazy [lite\|full\|ultra\|off]` | شدت اعمال نردبان سادگی |
| `/fix-one <گزارش> <شماره>` | ⭐ دقیقاً **یک** finding را اصلاح می‌کند |
| `/explain [commit\|--staged]` | توضیح می‌دهد چه تغییر کرد و چرا، در یک گزارش HTML — و چیزی که کسی نخواسته بود را علامت می‌زند |
| `/security-review [مسیر]` | دنبال نقص قابل‌سوءاستفاده می‌گردد — هر finding می‌گوید چه کسی و از چه راهی به آن می‌رسد |

`/fix-one` سخت‌گیرانه‌ترین قرارداد این مجموعه است — شش قدم اجباری:

۱. **اول تست شکست‌خورده.** اصلاحی که شکستش را نشان نداده، حدس است
۲. **علت واقعی، نه علامت.** `@ts-ignore`، `any`، `catch {}` خالی، `.skip()` ممنوع
۳. **کوچک‌ترین تغییر.** اگر اصلاح درست یعنی ریفکتور — بایست و بپرس
۴. **اثبات اصلاح.** تست جدید، کل سوئیت، typecheck
۵. **اثبات ماندن در دامنه.** `git diff --stat`؛ هر فایل اضافه drift است
۶. کامیت

#### `/explain` — رسید کار

روی هر دامنه‌ای اجرا می‌شود و یک گزارش HTML خودبسنده می‌سازد:

```
/explain                 # هرچه کامیت نشده — حالت معمول
/explain --staged        # درست قبل از کامیت
/explain HEAD            # یک کامیت، ذخیره در reports/<موضوع-کامیت>.html
/explain --project       # سند آشنایی با کل کدبیس
```

گزارش سه بخش مهم دارد: **چه چیزی برای کاربرِ اپ عوض شد**، **چه چیزی در کد عوض
شد** (گروه‌بندی‌شده بر اساس *دلیل*، نه پوشه)، و **ممیزی دامنه**.

ممیزی دامنه همان نکته است. هر فایل تغییرکرده باید به چیزی که خواستش برگردد —
خطی در `BRIEF.md`، یک finding شماره‌دار، سطری در `specs/`، یا پیام کامیت. هرچه
ردیابی نشود به‌عنوان `UNTRACED` با تعداد خطش گزارش می‌شود، با قالب سازگار
`/fix-one`:

```
- [ ] #2 UNTRACED app/Support/Formatter.php (+84/−0) — کلاس helper جدید
      کسی نخواسته بود: هیچ finding، خط بریف، یا سطر specs به این ارجاع ندارد
```

> «برای خوانایی ریفکتور شد» همان چیزی است که یک تغییر بی‌دلیل، وقتی مؤدبانه
> بیانش کنی، شبیهش می‌شود. به اسکیل گفته شده این جمله را ننویسد.

ممیزی تمیز هم یک نتیجهٔ واقعی است — اگر دیف کمینه باشد و همه‌چیز ردیابی شود،
صریحاً همین را می‌گوید.

### امنیت — سه لایه، نه یک دستور

امنیت نمی‌تواند اسکیلی باشد که یادت بیاید صدایش بزنی، چون لحظه‌ای که لازمش
داشتی از قبل گذشته. در سه جا می‌نشیند:

| کِی | چه چیزی | همیشه فعال؟ |
|---|---|---|
| **پلن** | قدم ۶ `/plan-check` — قدمی که از مرز اعتماد رد می‌شود باید از قبل بگوید چه کسی اجازه دارد، چه چیزی شکل ورودی را تأیید می‌کند، و چه شکلی خارج می‌شود | تو اجرا می‌کنی |
| **نوشتن** | بخش **Trust boundaries** در `CLAUDE.laravel.md` — تنها لایهٔ همیشه‌فعال | ✅ بله |
| **بازبینی** | `/security-review` — ممیزی لاراولی، سازگار با `/fix-one` | تو اجرا می‌کنی |

لایهٔ حین نوشتن عمداً در تمپلیت است نه در اسکیل، و یک قانون دارد که بر بقیه
اولویت دارد:

> **نردبان کد را کوچک می‌کند. مرز را هیچ‌وقت نازک نمی‌کند.**
> قوانین مرز اعتماد حتی زیر `/lazy ultra` هم برقرارند.

`/security-review` حول یک انضباط ساخته شده: **هر finding می‌گوید چه کسی و از
چه درخواستی به آن می‌رسد.** مسیر قابل‌دسترس نداشته باشد، finding نیست — می‌رود
در HARDENING. همین است که نمی‌گذارد گزارش امنیتی به چهل خط حدسی تبدیل شود که
کسی نمی‌خواندشان.

به ترتیبِ جایی می‌گردد که اپ‌های لاراولی واقعاً در آن می‌شکنند: Policy جاافتاده،
IDOR از راه route model binding، mass assignment به‌عنوان ارتقای سطح دسترسی،
بعد injection در جایی که از فریم‌ورک دور زده شده (`whereRaw`، `{!! !!}`،
`->orderBy($request->sort)`)، بعد آپلود، سشن، آنچه نشت می‌کند (API Resource که
کل مدل را برمی‌گرداند، سکرت در payload صف)، و آخر امضای وریفای‌نشدهٔ وبهوک.

> این یک خواندنِ کد است، نه تست نفوذ — و برای چیزی که با پول یا هویت سروکار
> دارد جایگزینش نمی‌شود. خود اسکیل هم همین را در خروجی‌اش می‌نویسد.

### موتور context — فقط Tier 3

`/ctx-audit` → `/ctx-interview` → `/ctx-generate` → `/ctx-verify` → `/ctx-learn`

> `git checkout CLAUDE.md` راه برگشتت است.

### زوم روی CODE — ستون شلوغ

<img src="assets/code-comparison.png" alt="داخل ستون CODE" width="100%">

تقریباً همهٔ ابزارهای کدنویسی AI آنجا رقابت می‌کنند، پس ارزشش را دارد دقیق
بگوییم کی چه می‌کند:

| | واقعاً چه چیزی را عوض می‌کند | چطور اعمال می‌شود | لاراول‌آگاه |
|---|---|---|---|
| **این جعبه‌ابزار** | نردبان ۷ پله + کانونشن‌ها در `CLAUDE.md` | متنی که مدل می‌خواند — **ضعیف‌ترین اعمال** | ✅ `casts`، `Gate::before`، constraint، اول `composer.json` |
| **ponytail** | همان ۷ پله، با عبارت عمومی | **هوک lifecycle** — تزریق در شروع سشن و tool-use | ❌ عمومی |
| **Laravel Boost** | اصول، N+1، کش، الگوهای امنیتی | اسکیل + MCP `search-docs` برای جواب نسخه‌دقیق | ✅ مال خود فریم‌ورک |
| **فقط CLAUDE.md** | هرچه خودت نوشتی | یک بار خوانده می‌شود، بعد زیر سشن دفن | بستگی به خودت |

دو چیز از این جدول درمی‌آید.

**نردبان‌ها یک ایده‌اند.** پله‌های این جعبه‌ابزار و ponytail تقریباً یک‌به‌یک
بر هم منطبق‌اند — YAGNI → بازاستفاده → stdlib → پلتفرم → پکیج نصب‌شده → یک خط
→ حداقل. فرقش این است که این یکی می‌گوید *«constraint دیتابیس بهتر از چک
اپلیکیشنی، `casts` بهتر از accessor+mutator»*، و نردبان عمومی نمی‌تواند.

**اعمال، ضعیف‌ترین نقطهٔ این جعبه‌ابزار است.** قانونی در `CLAUDE.md` یک بار
خوانده می‌شود و بعد از لحظهٔ نوشتن کد فاصله می‌گیرد. هوک ponytail سر خود
فراخوان ابزار شلیک می‌کند. اگر دیدی نردبان در سشن‌های طولانی drift می‌کند، آن
شکاف واقعی است — و همان دلیل صادقانهٔ سراغ ponytail رفتن.

> ⚠️ **تنها تضاد واقعی:** `/lazy` این جعبه‌ابزار و `/ponytail` هر دو یک مقدار
> `lite/full/ultra/off` را نگه می‌دارند، در دو جای مختلف. هر دو را نصب کنی،
> بی‌صدا با هم اختلاف پیدا می‌کنند — و متوجه نمی‌شوی، چون هر دو رفتار
> باورپذیرند.
>
> **اگر هر دو را می‌خواهی:** اسکیل `lazy` و بخش «Simplicity level» را از
> `CLAUDE.md` حذف کن، هفت پلهٔ لاراولی را نگه دار، و بگذار ponytail مالک مُد
> باشد.

## همراهان اختیاری — که عمداً اینجا کپی نشده‌اند

دو زنجیره‌ابزار بیرونی کنار این یکی خوب می‌نشینند. **هیچ‌کدام در این ریپو کپی
نشده‌اند و نباید بشوند** — هر دو اسکیل‌های خودشان را تولید و به‌روز می‌کنند، و
یک کپی منجمد بعد از اولین `composer update` دروغ می‌شود.

| ابزار | نصب | چه اضافه می‌کند |
|---|---|---|
| **Laravel Boost** | `composer require laravel/boost --dev` | `laravel-best-practices`، `infer-conventions`، `tailwindcss-development` + سرور MCP با `search-docs` |
| **OpenSpec** | `npm i -g openspec && openspec init` | `openspec-propose`، `openspec-apply-change`، `openspec-explore` و بقیه |

تقسیم کار:

- **این جعبه‌ابزار** → چه بسازیم و چقدر ساده نگهش داریم
- **OpenSpec** → این تغییر مشخص را چطور ببریم جلو
- **Boost** → لاراول را درست بنویس، با داکیومنت نسخه‌دقیق
