# specs — منبع حقیقت محصول

این پوشه **داخل همین ریپوی لاراوله** و با کد کامیت می‌شه. هر چیزی که تصمیمِ
محصوله نه جزئیاتِ پیاده‌سازی اینجاست: تعریف محصول، واژه‌نامه، ماتریس
دسترسی‌ها، فلوها، فهرست صفحات، و قرارداد سرویس‌های بیرونی.

## قانون طلایی

> **اول اینجا، بعد کد.** هر تغییری در مرزها (اسم موجودیت، مجوز جدید، صفحه
> جدید، سرویس بیرونی جدید) اول اینجا نوشته می‌شه، بعد پیاده‌سازی.
> کدی که با اینجا نمی‌خونه، باگه — حتی اگه کار کنه.

**مزیت اینکه specs داخل همین ریپوئه:** اسپک و کدش تو یک PR عوض می‌شن.
قرارداد کهنه بدتر از نداشتن قراردادِ، چون ایجنت بهش اعتماد می‌کنه.

## نقشه فایل‌ها

| فایل | چیه | کِی می‌خونمش/ویرایشش می‌کنم |
|---|---|---|
| `VISION.md` | یک صفحه: چی می‌سازیم و برای کی | یک بار می‌نویسی، کم عوض می‌شه |
| `ARCHITECTURE.md` | شکل سیستم، auth، پیش‌فرض‌های داده | تصمیم‌های زیرساختی اینجا ثبت می‌شن |
| `GLOSSARY.md` | واژه‌نامه فارسی ↔ انگلیسی ↔ شناسه کد | **قبل از ساخت هر موجودیت جدید** |
| `PERMISSIONS.md` | ماتریس نقش × قابلیت (سه پنل) | منبع Policy ها و سیدر نقش‌ها |
| `INTEGRATIONS.md` | سرویس‌های بیرونی که بهشون وصل می‌شیم + رفتار موقع قطعی | قبل از وصل شدن به هر سرویس |
| `FLOWS.md` | سناریوهایی که از مرز سرویس‌ها رد می‌شن | قبل از هر فیچر چندسرویسی |
| `PANELS.md` | فهرست صفحات سه پنل + مجوز هر صفحه | قبل از ساخت هر صفحه پنل |
| `BACKLOG.md` | لیست فیچرها، فقط عنوان + یک خط | برداشتن کار بعدی |
| `HOWTO.md` | **رودمپ پر کردن همه‌ی این فایل‌ها، با نمونه** | یک بار، اول پروژه |
| `contracts/*.openapi.yaml` | قرارداد سرویس‌های بیرونی (مرجع، مال ما نیست) | موقع نوشتن کلاینت |

## کی می‌نویسدشون؟ — تو یا Claude

**هیچ‌کدوم از این فایل‌ها رو با دست markdown نمی‌نویسی.** حرف می‌زنی، Claude
می‌نویسه. ولی خطِ فاصله مهمه:

**فقط تو تصمیم می‌گیری** (Claude حق حدس زدن نداره):

- `VISION.md` — محصول چیه، MVP کجاست، چی رو عمداً نمی‌سازیم
- `GLOSSARY.md` — اسم انگلیسی قطعی هر موجودیت
- `PERMISSIONS.md` — سطر به سطر، کی به چی دسترسی داره
- هر جای `[قلاب]` توی بقیه فایل‌ها

**Claude می‌نویسه، تو فقط تأیید/اصلاح می‌کنی:**

- `FLOWS.md` · `PANELS.md` · `contracts/*.yaml` و ساختارِ `INTEGRATIONS.md`
  — این‌ها از تصمیم‌های بالا **مشتق** می‌شن. اگه سه تای اول درست باشه،
  این‌ها رو Claude درست درمیاره.

> **چرا این تفکیک؟** Claude می‌تونه توصیف کنه چی **هست** و از تصمیم‌های تو
> نتیجه بگیره، ولی نمی‌تونه بدونه چی **باید** باشه. اگه بگی «خودت یه VISION
> بنویس»، یه محصول عمومیِ باورپذیر می‌نویسه که مال تو نیست — و بعد شش ماه
> روش کد می‌زنی.

### اگه از قبل یه سند کامل داری

سند ورد یا هر متن دیگه‌ای که نوشتی رو نده به سشن که خودش بخونه — بده به
`/spec-import`، چون اون **مسیریابی می‌کنه و جای خالی رو پر نمی‌کنه**:

```
> /clear
> /spec-import سند-من.docx
```

`.docx` خودش تبدیل می‌شه (`_toolkit/docx2md.py`، بدون نیاز به نصب چیزی).
خروجی‌اش دو تاست: فایل‌های پرشده، و **فهرست شکاف‌ها** — چیزهایی که سند
جوابشون رو نداده و عمداً حدس زده نشده.

بعدش `/clear` کن و فقط برای شکاف‌ها مصاحبه بزن، نه از اول.

**یک فایل = یک سشن = یک `/clear`.** پرامپت دقیق هر قدم، نمونه‌ی پرشده، و
مقایسه‌ی بد/خوب برای هر هشت فایل → [`HOWTO.md`](HOWTO.md).

## ساختار

```
project/            ← ریپوی لاراول
├── app/ database/ routes/ …
├── specs/          ← همین پوشه، با کد کامیت می‌شه
├── _toolkit/       ← ابزار Claude Code
└── .claude/skills/ ← ۱۵ تا skill، مخصوص همین پروژه
```

`claude` رو از **ریشه‌ی همین ریپو** بالا بیار — هم skillها لود می‌شن، هم
`@specs/...` مستقیم در دسترسه، هم `artisan` و `pint` بدون `cd` کار می‌کنن.

## ترتیب پر کردن (اول کار)

<!-- شرح کامل هر قدم با نمونه: HOWTO.md -->

1. `VISION.md` — یک سشن با Claude، سبک مصاحبه
2. `GLOSSARY.md` — موجودیت‌های اصلی رو لیست کن، اسم انگلیسی قطعی بده
3. `PERMISSIONS.md` — سطر به سطر تصمیم بگیر (پیش‌فرض‌ها چیده شدن)
4. `INTEGRATIONS.md` — برای هر سرویس بیرونی، مخصوصاً خط «وقتی بالا نیست»
5. `FLOWS.md` — فقط فلوهای milestone صفر. بقیه رو وقتی نوبتشون شد.
6. `PANELS.md` — فهرست صفحات، یک ردیف هر صفحه. جزئیات صفحه اینجا نه.
7. `contracts/` — اسکلت‌ها هستن؛ هر endpoint واقعی که تصمیمش قطعی شد اضافه کن
8. `BACKLOG.md` — milestone صفر (برش نازک) از قبل نوشته شده؛ بقیه رو بچین

## کجا چی بنویسم — جدول تصمیم

| چی می‌خوام بنویسم | کجا | چقدر |
|---|---|---|
| ایده‌ی یه فیچر | `BACKLOG.md` | عنوان + یک خط. تمام. |
| سناریویی که به سرویس بیرونی می‌خوره | `FLOWS.md` | ~۲۵ خط، با بخش «اگه خراب شد» |
| یه سرویس بیرونی جدید | `INTEGRATIONS.md` | نصف صفحه + رفتار قطعی |
| سناریوی داخل خود اپ | `BRIEF.md`، موقع ساخت | سقف ۳۰ خط |
| اینکه پنل چه صفحاتی داره | `PANELS.md` | یک ردیف جدول |
| اینکه یه صفحه چه فیلدی داره | `BRIEF.md`، موقع ساخت همون صفحه | — |
| کی به چی دسترسی داره | `PERMISSIONS.md` | یک سطر ماتریس |
| شکل دقیق request/response سرویس بیرونی | `contracts/*.openapi.yaml` | — |
| اسم انگلیسی یه موجودیت | `GLOSSARY.md` | **قبل از ساختش** |
| تصمیم زیرساختی و دلیلش | `ARCHITECTURE.md` | — |

> **قانونی که بیشتر از همه زیر پا می‌ذاری:** جزئیات فیچر رو از قبل ننویس.
> `BACKLOG.md` عنوانه، `FLOWS.md` اتصاله، و جزئیات فقط روزی نوشته می‌شه که
> قراره ساخته بشه — با `/brief`. جزئیاتِ سه ماه زودتر نوشته‌شده، روز ساخت
> باطل شده، ولی ایجنت هنوز جدی می‌گیردش.
