## قالب هر فلو

```
### <اسم فلو>
**بازیگر:** <نقش از PERMISSIONS.md>   **شروع:** <کجا کلیک می‌شه / چی تریگرش می‌کنه>
**سرویس‌های درگیر:** a → b → c

1. <سرویس>: <کاری که می‌کنه> → <چی برمی‌گردونه یا publish می‌کنه>
2. ...

**تمام شد یعنی:** <یک جمله قابل مشاهده — چیزی که یه آدم می‌بینه>
**اگه خراب شد:** <مهم‌ترین شکست + کاربر چی می‌بینه + سیستم در چه حالتی می‌مونه>
```

بخش «اگه خراب شد» اختیاری نیست. فلویی که فقط مسیر موفقش نوشته شده، نصفه‌ست
و ایجنت نصفه‌ی دومش رو خودش از خودش درمیاره.

## ثبت‌نام و ورود با OTP ⭐ (Milestone 0)

**بازیگر:** مهمان   **شروع:** فرم ثبت‌نام در core
**سرویس‌های درگیر:** core → identity → notification

1. core: موبایل رو می‌گیره، به identity پاس می‌ده (خودش هیچ کاربری نمی‌سازه)
2. identity: کاربر `pending` می‌سازه یا برمی‌داره، OTP تولید می‌کنه (TTL [۲ دقیقه])
3. identity: به API notification می‌زنه تا OTP تحویل بشه — مستقیم SMS نمی‌فرسته
4. notification: طبق قالب می‌فرسته (driver `log` در dev) و لاگ ارسال نگه می‌داره
5. کاربر کد رو وارد می‌کنه → identity تأیید می‌کنه → JWT (RS256) + refresh می‌ده
6. identity: `identity.user_registered` را publish می‌کند (فقط بار اول)
7. core: session روی Redis می‌سازه و می‌بره به پنل کاربر

**تمام شد یعنی:** یه غریبه ثبت‌نام می‌کنه، کد رو (از لاگ) می‌زنه، پروفایل
خودش رو توی پنل کاربر می‌بینه.
**اگه خراب شد:** notification بالا نیست → identity کد رو ساخته ولی تحویل نشده.
کاربر پیام «کد ارسال نشد، دوباره تلاش کن» می‌بینه، کاربر `pending` می‌مونه و
تلاش بعدی همون کد قبلی رو تا انقضا دوباره می‌فرسته — نه کد جدید.
[تصمیم بگیر: سقف تلاش و پنجره rate limit چقدره؟]

## Checkout — اعمال تخفیف و پرداخت (Milestone 1)

**بازیگر:** کاربر (`payments.create_own` + `discounts.redeem`)
**شروع:** دکمه پرداخت در core
**سرویس‌های درگیر:** core → discount → payment → (webhook) → core → notification

1. core: [سبد/سفارش] رو نهایی می‌کنه، مبلغ رو به [ریال، واحد صحیح] حساب می‌کنه
2. discount: کد رو **اعتبارسنجی** می‌کنه و مبلغ نهایی رو برمی‌گردونه — هنوز مصرف ثبت نمی‌شه
3. payment: پرداخت با مبلغ نهایی می‌سازه، لینک درگاه می‌ده
4. کاربر می‌ره درگاه و برمی‌گرده
5. payment: **webhook** درگاه منبع حقیقته، نه بازگشت کاربر. idempotent روی شناسه تراکنش
6. payment: `payment.payment_succeeded` یا `payment.payment_failed` را publish می‌کند
7. core: مصرف کد تخفیف را **بعد از موفقیت** در discount ثبت می‌کند
8. notification: رسید را می‌فرستد

**تمام شد یعنی:** سفارش `paid` است، کد یک بار مصرف خورده، کاربر رسید گرفته.
**اگه خراب شد:** کاربر پول داده ولی webhook نرسیده → سفارش `pending` می‌مونه،
هیچ کد تخفیفی مصرف نشده، و [job آشتی‌دهنده / بررسی دستی] وضعیت را از payment
می‌پرسد. **هرگز** بر اساس بازگشت کاربر از درگاه، سفارش را paid نکن.
