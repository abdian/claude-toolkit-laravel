## سه قانونی که کل این رودمپ روشون سواره

**۱. تو تصمیم می‌گیری، Claude می‌نویسه.**
هیچ‌کدوم از این فایل‌ها رو با دست markdown نمی‌نویسی. فارسیِ شلخته حرف می‌زنی،
اون مرتب می‌کنه و فایل رو می‌سازه. ولی *تصمیم* هیچ‌وقت واگذار نمی‌شه — چون
Claude می‌تونه توصیف کنه چی **هست**، نمی‌تونه بدونه چی **باید** باشه.

**۲. یک فایل = یک سشن = یک `/clear`.**
دو تا فایل رو تو یک سشن نچپون. تا وسط فایل دوم، context پر شده و کیفیت
سؤال‌ها می‌ریزه — و تو متوجه نمی‌شی، چون جواب‌ها هنوز باورپذیرن.

**۳. جزئیاتِ زودتر از موعد = جزئیاتِ باطل.**
هیچ‌جای این هشت قدم، جزئیات یک فیچر نوشته نمی‌شه. تا `contracts/` هم فقط
endpoint هایی می‌رن که تصمیمشون قطعیه. جزئیات روز ساخت، با `/brief`.

## محصول نمونه‌ی این راهنما

برای اینکه نمونه‌ها واقعی باشن نه انتزاعی، کل این فایل از یک محصول فرضی
استفاده می‌کنه: **«دوره‌یار» — فروش دوره ویدیویی آموزشی**. مدرس دوره می‌ذاره،
کاربر می‌خره و تماشا می‌کنه، ادمین نظارت می‌کنه.

هر جا `▸ نمونه` دیدی، مال همینه. مال خودت رو بذار جاش.

# قدم ۱ — `VISION.md`

**کی می‌نویسه:** تو. این تنها فایلیه که Claude حق نداره حتی پیش‌نویسش رو بزنه.
اگه بگی «خودت بنویس»، یه محصول عمومیِ باورپذیر می‌نویسه که مال تو نیست، و بعد
شش ماه روش کد می‌زنی.

### پرامپت

```
> /clear
> @specs/VISION.md رو باز کن.
  با سبک مصاحبه سؤال‌به‌سؤال کمکم کن پرش کنم — یکی یکی بپرس، نه لیستی.
  جواب‌هام فارسیِ شلخته‌ست، خودت مرتب کن.
  روی بخش Non-goals سخت‌گیر باش: تا سه تا چیز که عمداً نمی‌سازم نگفتم، ولم نکن.
```

### ▸ نمونه‌ی پرشده

```markdown
## محصول در یک جمله

جایی که یک مدرس بتواند دوره‌ی ویدیویی‌اش را بفروشد بدون اینکه درگیر درگاه
پرداخت، هاست ویدیو و پشتیبانی مالی شود.

## کاربرها

| نقش | کیه | مهم‌ترین کاری که باید بتونه بکنه |
|---|---|---|
| کاربر | کسی که دنبال یادگیری یک مهارت مشخص است | دوره بخرد و بدون قطعی تماشا کند |
| ادمین | پشتیبانی ما | ببیند پرداخت یک کاربر چرا نشسته و رفعش کند |
| سوپرادمین | تیم فنی | مدرس تأیید کند، تسویه بزند، تنظیمات سیستم |

## MVP — کوچیک‌ترین نسخه‌ای که ارزش داره

کاربر با موبایل ثبت‌نام می‌کند، یک دوره را با کد تخفیف اختیاری می‌خرد،
پرداخت موفق می‌شود، و بلافاصله ویدیوها را در پنل خودش می‌بیند.
یک مدرس، یک دوره، یک درگاه. همین.

## Non-goals — چیزهایی که عمداً نمی‌سازیم

- آزمون و مدرک — نسخه دو، اگر اصلاً
- اپ موبایل — وب ریسپانسیو کافی است
- چند‌زبانه — فقط فارسی
- اشتراک ماهانه — فعلاً فقط خرید تکیِ دوره
```

### بد ↔ خوب

| ✗ | ✓ |
|---|---|
| «یک پلتفرم جامع آموزشی مدرن و مقیاس‌پذیر» | «جایی که یک مدرس دوره‌اش را بفروشد بدون درگیری با درگاه و هاست ویدیو» |
| Non-goals خالی | سه تا چیز مشخص با دلیل |
| «کاربر: افرادی که می‌خواهند یاد بگیرند» | «کاربر: کسی که دنبال یک مهارت مشخص است» |

**علامت اینکه بد نوشتی:** جمله‌ات را برای یک محصول دیگر هم می‌شود گفت.

### تمام شد یعنی

- [ ] جمله‌ی اول، اسم هیچ تکنولوژی‌ای ندارد
- [ ] MVP در ۵ خط جا شده و به یک فلوی قابل نمایش اشاره می‌کند
- [ ] حداقل ۳ تا Non-goal دارد

# قدم ۲ — `GLOSSARY.md` ⚠️

**کی می‌نویسه:** تو. Claude پیشنهاد اسم می‌دهد، تصمیم با تو.

**چرا بحرانی‌ترین قدم است:** اسمی که اینجا قطعی می‌کنی، به جدول دیتابیس، کلاس
مدل، فیلد JSON، پارامتر URL و اسم event تبدیل می‌شود — در شش ریپوی جدا. عوض
کردنش در ماه سوم یعنی rename هماهنگ در همه‌شان + مایگریشن + شکستن قرارداد
سرویس‌های دیگر. یک ساعت دقت اینجا، معادل چند روز بعداً.

بدون این فایل، Claude در هر سشن یک اسم جدید می‌سازد:
`Discount` / `Coupon` / `PromoCode` / `Voucher` — همه برای یک چیز.

### پرامپت

```
> /clear
> @specs/GLOSSARY.md و @specs/VISION.md رو باز کن.
  از VISION موجودیت‌های دامنه‌ی محصول رو دربیار و بهم پیشنهاد بده،
  برای هرکدوم دو تا اسم انگلیسی جایگزین بده و بگو هرکدوم چه دردسری داره.
  من انتخاب می‌کنم. ستون مالک فقط دو مقدار داره: «این اپ» یا «بیرونی: <نام>».
  ردیف‌های [؟] رو خودت تصمیم نگیر — بپرس.
```

### ▸ نمونه — ردیف‌های اضافه‌شده برای «دوره‌یار»

```markdown
| فارسی | English | شناسه در کد | مالک | تعریف یک‌خطی |
|---|---|---|---|---|
| دوره | Course | `Course` / `courses` | core | یک بسته آموزشی قابل خرید |
| فصل | Chapter | `Chapter` / `chapters` | core | گروه‌بندی درس‌ها داخل یک دوره |
| درس | Lesson | `Lesson` / `lessons` | core | یک ویدیو + توضیح؛ کوچک‌ترین واحد تماشا |
| مدرس | Instructor | `Instructor` / `instructors` | core | کاربری که دوره منتشر می‌کند |
| ثبت‌نام در دوره | Enrollment | `Enrollment` / `enrollments` | core | دسترسی یک کاربر به یک دوره پس از خرید |
| پیشرفت | Progress | `Progress` / `progress` | core | کدام درس‌ها را تا کجا دیده |
```

**تصمیم‌هایی که در همین جدول گرفته شد و اگر گرفته نمی‌شد، فردا دعوا می‌شد:**

- `Enrollment` انتخاب شد نه `Purchase`. چون خرید مال سرویس `payment` است؛
  چیزی که `core` مالکش است «دسترسی» است. هدیه‌دادن یک دوره هم `Enrollment`
  می‌سازد بدون اینکه `Payment` داشته باشد.
- `Lesson` نه `Video`. چون فردا درس متنی یا فایل پیوست اضافه می‌شود و
  `Video` آن موقع دروغ می‌شود.
- `Instructor` جدا از `User` است، ولی کاربرِ پشتش در `identity` می‌ماند —
  یعنی `instructors.user_id` یک **UUID** است، نه FK.

### بد ↔ خوب

| ✗ | ✓ | چرا |
|---|---|---|
| `Video` | `Lesson` | فردا درس غیرویدیویی می‌آید |
| `Purchase` در core | `Enrollment` در core | خرید مال payment است، دسترسی مال core |
| `Item` `Data` `Info` `Manager` | اسم دامنه | اسم بی‌معنا، اسم نیست |
| فارسی: «دوره»، انگلیسی: «Doreh» | `Course` | فینگلیش در کد ممنوع |

### تمام شد یعنی

- [ ] هر موجودیتِ دامنه‌ی محصولت یک ردیف دارد
- [ ] ستون «مالک» هر ردیف دقیقاً یک سرویس است (نه دو تا)
- [ ] enum های وضعیت (`draft`/`published`/…) در بخش دوم فایل هستند
- [ ] هیچ ردیفی `[قلاب]` باقی نمانده

# قدم ۳ — `PERMISSIONS.md`

**کی می‌نویسه:** تو، سطر به سطر. پیش‌فرض‌ها چیده شده‌اند ولی چند جا `[✓؟]`
دارد — آن‌ها تصمیم کسب‌وکار است، نه فنی. مثلاً «ادمین بتواند استرداد بزند؟»

این جدول مستقیم تبدیل می‌شود به: سیدر نقش‌ها + Policy ها + `permissions[]`
داخل JWT + منوی هر پنل. یعنی چهار جا از یک منبع.

### پرامپت

```
> /clear
> @specs/PERMISSIONS.md و @specs/GLOSSARY.md رو باز کن.
  اول: برای موجودیت‌های جدید GLOSSARY یه بخش مجوز پیشنهاد بده.
  بعد: همه‌ی [✓؟] ها رو یکی‌یکی ازم بپرس و برای هرکدوم بگو
  اگه بدم چه ریسکی داره و اگه ندم چه دردسری داره. خودت تصمیم نگیر.
```

### ▸ نمونه — بخش جدید برای «دوره‌یار»

```markdown
## دوره‌ها — core

| مجوز | super_admin | admin | user | توضیح |
|---|:-:|:-:|:-:|---|
| `courses.view_published` | ✓ | ✓ | ✓ | دیدن دوره‌های منتشرشده |
| `courses.view_own_enrolled` | ✓ | ✓ | ✓ | تماشای دوره‌ای که خریده |
| `courses.manage_own` | — | — | ✓* | مدرس: ساخت/ویرایش دوره‌ی خودش |
| `courses.publish` | ✓ | ✓ | — | تأیید و انتشار دوره‌ی یک مدرس |
| `courses.view_any` | ✓ | ✓ | — | دیدن همه دوره‌ها شامل پیش‌نویس‌ها |

* مدرس نقش جدا نیست، کاربری است که `courses.manage_own` گرفته.
  [تصمیم: نقش چهارم `instructor` بسازیم یا مجوز روی user کافی است؟ → مجوز کافی است،
  چون فقط همین یک تفاوت را دارد. نقش چهارم یعنی چهار ستون در همه‌ی جدول‌ها.]
```

**آن پرانتز، مهم‌ترین چیز این فایل است.** تصمیم *و دلیلش* را کنار خود سطر
بنویس. سه ماه بعد که کسی می‌پرسد «چرا نقش instructor نداریم؟» جواب همان‌جاست.

### بد ↔ خوب

| ✗ | ✓ |
|---|---|
| `courses.edit` | `courses.manage_own` و `courses.view_any` جدا |
| چک با `$user->role === 'admin'` | چک با `can('courses.publish')` |
| مجوزی که هیچ صفحه‌ای در PANELS ندارد | هر مجوز حداقل یک مصرف‌کننده دارد |

### تمام شد یعنی

- [ ] هیچ `[✓؟]` باقی نمانده
- [ ] هر تصمیم غیربدیهی، دلیلش کنارش نوشته شده
- [ ] نام‌ها `domain.action` اند و `domain` با GLOSSARY می‌خواند

# قدم ۴ — `INTEGRATIONS.md`

**کی می‌نویسه:** Claude ساختار را می‌نویسد، **تو خط «وقتی بالا نیست» را
تصمیم می‌گیری**. آن خط تصمیم محصول است، نه فنی — و اگر ننویسی، هر بار یک

این اپ مالک هیچ سرویس بیرونی نیست. چیزی که اینجا می‌نویسی «شناسنامه‌ی
سرویس‌های خودم» نیست، «قرارداد سرویس‌هایی که بهشان وصل می‌شوم» است.

### پرامپت

```
> /clear
> @specs/INTEGRATIONS.md @specs/VISION.md @specs/GLOSSARY.md
  برای هر سرویس بیرونی، بخشش رو طبق قالب کامل کن.
  برای «وقتی بالا نیست» خودت تصمیم نگیر — دو تا گزینه بده و بپرس،
  و بگو هرکدوم کاربر چی می‌بینه و سیستم تو چه حالتی می‌مونه.
```

### ▸ نمونه — بخش پرداخت پرشده

```markdown
## پرداخت — زرین‌پال

- **برای چی:** دریافت وجه بابت خرید دوره
- **کلاینت:** `app/Services/PaymentClient.php`
- **آدرس/تنظیمات:** `config/services.php` → `payment` · env: `PAYMENT_MERCHANT_ID`
- **احراز هویت:** merchant id در بدنه‌ی درخواست
- **چی ازش می‌خوایم:** ساخت تراکنش · تأیید تراکنش
- **وقتی بالا نیست:** دکمه خرید غیرفعال با پیام «درگاه در دسترس نیست».
  سفارش ساخته نمی‌شود، جای دوره رزرو نمی‌شود.
- **چی نگه می‌داریم:** `payments.external_id` + `status` خودمان.
  مبلغ عدد صحیح، واحد ریال.
```

**دو تصمیمی که در همین ده خط گرفته شد و هر دو محصولی بودند:** اینکه موقع
قطعی درگاه سفارشِ `pending` ساخته **نشود** (تا سفارش سرگردان نماند)، و اینکه
جای دوره رزرو نشود.

### بد ↔ خوب

| ✗ | ✓ |
|---|---|
| «اگر خطا داد، خطا نشان بده» | رفتار دقیق + وضعیتی که سیستم در آن می‌ماند |
| `Http::get()` در کنترلر | فقط در `app/Services/<Name>Client.php` |
| ذخیره‌ی کپی پروفایل کاربر | فقط `external_id`؛ بقیه را از کلاینت بپرس |
| FK به شناسه‌ی سرویس بیرونی | ستون ساده، بدون FK و بدون join |

### تمام شد یعنی

- [ ] هر سرویس بیرونی خط «وقتی بالا نیست» دارد و خالی نیست
- [ ] برای هرکدام مشخص است چه چیزی را نگه می‌داریم و چه چیزی را نه
- [ ] هیچ سرویسی که هنوز بهش وصل نشدی، نوشته نشده

# قدم ۵ — `FLOWS.md`

**کی می‌نویسه:** Claude مسیر موفق را می‌نویسد، **تو بخش «اگه خراب شد» را
تصمیم می‌گیری**. آن بخش را واگذار نکن — همان‌جاست که تصمیم کسب‌وکار پنهان است.

فقط فلویی که به یک سرویس بیرونی می‌خورد. فلوی کاملاً داخلی اینجا نمی‌آید —
آن `/brief` است، روز ساخت.

### پرامپت

```
> /clear
> @specs/FLOWS.md @specs/INTEGRATIONS.md @specs/BACKLOG.md
  فقط برای فلوهای Milestone 0 و 1 بنویس، نه بیشتر.
  مسیر موفق رو خودت بنویس. برای هر فلو، دو تا نقطه‌ی شکستِ محتمل
  رو بهم نشون بده و بپرس هرکدوم چی باید بشه — خودت تصمیم نگیر.
```

### ▸ نمونه — فلوی خرید دوره

```markdown
### خرید دوره
**بازیگر:** کاربر (`payments.create_own`)   **شروع:** دکمه «خرید» در صفحه دوره
**سرویس‌های درگیر:** core → discount → payment → (webhook) → core → notification

1. core: چک می‌کند کاربر قبلاً `Enrollment` این دوره را ندارد
2. discount: کد را اعتبارسنجی می‌کند، مبلغ نهایی برمی‌گردد — مصرف ثبت نمی‌شود
3. payment: پرداخت با مبلغ نهایی می‌سازد، لینک درگاه می‌دهد
4. کاربر می‌رود درگاه و برمی‌گردد
5. payment: **webhook** منبع حقیقت است، نه بازگشت کاربر. idempotent روی شناسه تراکنش
6. payment: `payment.payment_succeeded` را publish می‌کند
7. core: `Enrollment` می‌سازد و مصرف کد را در discount ثبت می‌کند
8. notification: پیامک «دوره فعال شد» می‌فرستد

**تمام شد یعنی:** کاربر درس اول را در پنل خودش می‌بیند و می‌تواند پخش کند.
**اگه خراب شد:**
- پول رفته، webhook نرسیده → `Enrollment` ساخته نمی‌شود، کد مصرف نمی‌شود،
  کاربر پیام «پرداخت در حال بررسی» می‌بیند. **هرگز** با بازگشت کاربر از
  درگاه دسترسی نده.
- webhook دو بار رسید → بار دوم no-op. `Enrollment` تکراری ساخته نمی‌شود
  (unique روی `user_id + course_id`).
```

**دقت کن دو تا تصمیم واقعی اینجا گرفته شد** که هیچ‌کدام فنی نبودند: اینکه
کاربرِ منتظرِ webhook چه پیامی ببیند، و اینکه دسترسی هرگز از redirect ساخته
نشود. اگر این‌ها را ننویسی، ایجنت روز ساخت خودش یکی از خودش درمی‌آورد.

### تمام شد یعنی

- [ ] هر فلو بخش «اگه خراب شد» دارد و خالی نیست
- [ ] هیچ فلویی از ۲۵ خط رد نشده (رد شد = دو تا فلو است)
- [ ] فلوی داخل یک سرویس اینجا نیامده

# قدم ۶ — `PANELS.md`

**کی می‌نویسه:** Claude، مستقیم از `PERMISSIONS.md`. تو فقط صفحات دامنه‌ی
محصولت را اضافه می‌کنی.

### پرامپت

```
  ردیف‌های مربوط به دوره‌ها رو به هر سه پنل اضافه کن.
  ستون مجوز فقط از PERMISSIONS بیاد — مجوز جدید از خودت نساز؛
  اگه صفحه‌ای مجوز نداره، بگو تا اول اونجا اضافه کنم.
```

### ▸ نمونه — ردیف‌های اضافه‌شده

```markdown
## پنل کاربر — /panel
| دوره‌های من | `/panel/courses` | `courses.view_own_enrolled` | دوره‌های خریداری‌شده + درصد پیشرفت | ادامه تماشا |
| تماشای درس | `/panel/courses/{course}/{lesson}` | `courses.view_own_enrolled` | پخش‌کننده + لیست درس‌ها | علامت «دیدم» |
| دوره‌های من (مدرس) | `/panel/teaching` | `courses.manage_own` | دوره‌های خودش + وضعیت تأیید | ساخت دوره |

## پنل ادمین — /admin
| دوره‌ها | `/admin/courses` | `courses.view_any` | همه دوره‌ها + فیلتر وضعیت | تأیید/رد (`courses.publish`) |
| ثبت‌نام‌ها | `/admin/enrollments` | `courses.view_any` | چه کسی چه دوره‌ای دارد | ثبت‌نام دستی |
```

**دقت:** «تماشای درس» یک ردیف جداست چون صفحه‌ی جداست، ولی چیزهایی مثل
«لیست درس‌ها در کنار پخش‌کننده» ردیف نیست — بخشی از همان صفحه است. این خط،
مرزِ «ردیف جدید یا نه» است.

چیزی که اینجا **نمی‌نویسی**: ستون‌های جدول، فیلترها، اعتبارسنجی فرم، چیدمان.
همه‌ی این‌ها روز ساخت همان صفحه، در `/brief`.

### تمام شد یعنی

- [ ] هر ردیف، مجوزش واقعاً در `PERMISSIONS.md` وجود دارد
- [ ] هیچ وایرفریم و لیست فیلدی وارد فایل نشده
- [ ] پنل سوپرادمین چیزهای ادمین را تکرار نکرده

# قدم ۷ — `contracts/*.openapi.yaml`

**کی می‌نویسه:** Claude. تو فقط جلوی زیاده‌روی‌اش را می‌گیری.

**تنها قانون این قدم:** فقط endpoint هایی که در `FLOWS.md` و `PANELS.md` واقعاً
لازم شدند. نه یک تای بیشتر. وسوسه‌ی «حالا که داریم می‌نویسیم، CRUD کاملش را
هم بزنیم» دقیقاً همان چیزی است که این جعبه‌ابزار برایش ساخته شده.

### پرامپت

```
> /clear
> @specs/contracts/identity.openapi.yaml @specs/FLOWS.md @specs/PANELS.md
  فقط endpoint هایی که تو FLOWS یا PANELS واقعاً استفاده شدن رو اضافه کن.
  برای هر کدوم بگو کدوم خط از کدوم فایل لازمش کرده.
  اگه endpointـی به ذهنت رسید که هیچ‌جا لازم نشده، ننویسش — فقط اسمشو بگو.
```

آن خط آخر مهم است: پیشنهادش را می‌گیری بدون اینکه فایل باد کند.

### ▸ نمونه

```yaml
  /courses/{course}/enroll:
    post:
      summary: Grant access after a successful payment
      # لازم شده در: FLOWS.md «خرید دوره» مرحله ۷
      # فراخوان: فقط core، بعد از دریافت payment.payment_succeeded
      requestBody:
        content:
          application/json:
            schema:
              type: object
              required: [user_id, payment_id]
              properties:
                user_id:   { type: string, format: uuid }
                payment_id: { type: string, format: uuid }
      responses:
        "201": { description: Enrollment created }
        "409": { description: Already enrolled — idempotent, not an error }
```

آن دو خط کامنت (`لازم شده در` / `فراخوان`) ارزشش را دارند: شش ماه بعد که کسی
می‌پرسد این endpoint برای چیست، جواب همان‌جاست — و اگر آن فلو حذف شد، معلوم
می‌شود این هم باید حذف شود.

### تمام شد یعنی

- [ ] هر endpoint به یک خط از FLOWS یا یک ردیف از PANELS ردیابی می‌شود
- [ ] پاسخ‌های خطای مهم (۴۰۹، ۴۲۲، ۴۰۳) نوشته شده‌اند، نه فقط ۲۰۰
- [ ] هیچ endpointـی «برای بعداً» نوشته نشده

# بعد از این هشت قدم چه اتفاقی می‌افتد

specs تمام شد ≠ کد شروع شد. یک قدم وسط هست:

```
specs آماده
   ↓
هر ریپوی سرویس: CLAUDE.md از templates/CLAUDE.laravel.md.template
   ↓ (توی بخش Architecture یک خط:)
   «Contracts: ../specs/contracts/<this>.openapi.yaml — API باید باهاش بخونه.
    مدل داده مشترک: ../specs/GLOSSARY.md»
   ↓
یک آیتم از BACKLOG برمی‌داری  →  /brief  →  اینجا تازه جزئیات نوشته می‌شود
   ↓
plan mode  →  /clear  →  /plan-check  →  کد  →  تست  →  /code-review
```

**نقطه‌ای که بیشترین آدم اشتباه می‌کند:** بعد از specs مستقیم می‌روند سراغ کد.
`CLAUDE.md` هر سرویس، چیزی است که وصل می‌کند این هشت فایل را به کدی که واقعاً
نوشته می‌شود. بدون آن، specs یک پوشه‌ی مستندات است که هیچ‌کس نمی‌خواندش.

# پنج اشتباه رایج

**۱. همه را در یک سشن نوشتن.**
تا فایل سوم، context پر است. جواب‌ها هنوز باورپذیرند ولی دیگر به VISION وصل
نیستند. `/clear` بین هر فایل.

**۲. گذاشتن جزئیات فیچر در specs.**
اگر خودت را در حال نوشتن «فرم باید این فیلدها را داشته باشد» دیدی، در فایل
اشتباهی هستی. آن `/brief` است، روز ساخت.

**۳. سپردن VISION یا GLOSSARY به Claude.**
خروجی‌اش تمیز و باورپذیر است و دقیقاً به همین دلیل خطرناک است: هیچ‌وقت
متوجه نمی‌شوی که تصمیمی گرفته نشده، فقط پر شده.

**۴. نوشتن فقط مسیر موفق در FLOWS.**
نصف باگ‌های تولید، در نصف نانوشته‌ی فلو هستند.

**۵. آپدیت نکردن specs بعد از تغییر.**
قرارداد کهنه بدتر از نداشتن قرارداد است، چون ایجنت به آن اعتماد می‌کند. تغییر
مرز سرویس‌ها → اول اینجا کامیت، بعد کد. (قانون طلایی README).
