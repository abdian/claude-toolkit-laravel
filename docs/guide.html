01

نصب

جعبه‌ابزار رو می‌ذاری داخل پروژه و از داخلش نصب می‌کنی.

روش سریع

cd _toolkit
bash install.sh

این شش ابزار پایه رو نصب می‌کنه: start، next، brief، plan-check، fix-one، lazy. با همین شروع کن.

گزینه‌های دیگه

bash install.sh --all              # هر هفده تا
bash install.sh --all --global     # تو ~/.claude/skills به‌جای پروژه
bash install.sh --all --force      # چیزی که هست رو بازنویسی کن

پیش‌فرض پروژه‌ای و symlinkـه: ابزارها می‌رن تو .claude/skills/ همون پروژه و ویرایش skills/ فوراً اعمال می‌شه. جایی که symlink واقعی ممکن نباشه (ویندوز بدون Developer Mode) اسکریپت کپی نصب می‌کنه و خودش بهت می‌گه — اون‌وقت بعد از هر ویرایش --force لازمه.

بررسی نصب

داخل Claude Code بزن:

/skills   # لیست ابزارها
/doctor   # اگه چیزی پیدا نشد، دلیلش رو می‌گه

یک skill شخصی، skill پروژه‌ای هم‌نام رو کنار می‌زنه. اگه قبلاً سراسری نصب کرده بودی، نصب پروژه‌ای هیچ اثری نداره و هنوز نسخه‌ی قدیمی اجرا می‌شه — یا ~/.claude/skills/ رو پاک کن، یا با --global همون رو به‌روز کن.

اگه دستورها نیومدن: skill پروژه‌ای از پوشه‌ای لود می‌شه که claude رو از داخلش اجرا کردی، نه از پوشه‌های بالاتر — اول چک کن از ریشه پروژه اجراش کرده باشی. برای نصب سراسری، اگه ~/.claude/skills تازه ساخته شده یک بار ری‌استارت لازمه.

ویندوز: install.sh رو از Git Bash یا WSL اجرا کن، نه cmd/PowerShell.

قانون کامیت — اختیاری، پیشنهادی

دو لایه: قانون (تمپلیت CLAUDE.md.template حالا بخش Git — commit policy داره: کامیت فقط با دستور صریح تو، هیچ اسمی از Claude هیچ‌جای کامیت) + اجرای قطعی — محتوای templates/settings.json.template رو کپی کن تو ~/.claude/settings.json:

{
  "attribution": { "commit": "", "pr": "" },
  "permissions": { "ask": ["Bash(git commit:*)"] }
}

attribution خالی → حذف قطعی Co-Authored-By و footer. ask → هر کامیت قبل از اجرا ازت تأیید می‌گیره. includeCoAuthoredBy منسوخه — همزمان با attribution استفاده‌ش نکن.

02

نقشه فایل‌ها

دو جای مختلف. ابزارها یک‌جا، خروجی‌ها جای دیگه.

ابزارها — سراسری

پیش‌فرض داخل خود پروژه نصب می‌شن، پس قابل کامیت‌ان و هر پروژه می‌تونه نسخه‌ی خودش رو داشته باشه. با --global به‌جاش تو ~/.claude/skills/ می‌شینن (~ یعنی پوشه خونه‌ات).

my-project/ ├── _toolkit/ ← خود جعبه‌ابزار، تو گیت │ ├── install.sh │ ├── docx2md.py ← مبدل docx برای /spec-import │ ├── skills/ ← منبع اصلی، اینجا ویرایشش می‌کنی │ └── templates/ └── .claude/skills/ ← install.sh اینجا لینک می‌کنه ├── start/SKILL.md ← در ورودی ├── next/SKILL.md ← راننده روزمره ├── brief/SKILL.md ← چی می‌سازیم ├── spec-import/ ← سند شلخته → specs/ ├── edges/SKILL.md ← حالت‌های مرزی ├── plan-check/SKILL.md ← داور پلن، قبل از کد ├── fix-one/SKILL.md ← اصلاح تکی ├── lazy/SKILL.md ← شدت سخت‌گیری نردبان ├── debt/SKILL.md ← دفتر میان‌برهای عمدی ├── ctx-audit/SKILL.md ┐ ├── ctx-interview/SKILL.md │ ├── ctx-generate/SKILL.md ├ موتور context ├── ctx-verify/SKILL.md │ (فقط پروژه بزرگ) ├── ctx-learn/SKILL.md ┘ ├── audit-codebase/SKILL.md ┐ ممیزی └── find-overengineering/SKILL.md ┘ (فقط پروژه بزرگ)

اسم پوشه = اسم دستور. پوشه fix-one می‌شه دستور /fix-one. همین. اسم داخل فایل فقط برچسب نمایشیه.

خروجی‌ها — داخل هر پروژه

اینا رو تو گیت بذار. تاریخچه تصمیم‌هاتن.

my-project/ ├── PROJECT.md ← /start می‌سازتش ├── BRIEF.md ← /brief می‌سازتش ├── CLAUDE.md ← تولیدشده ├── AUDIT.md ← چک‌لیست باگ‌ها ├── COMPLEXITY.md ← پیچیدگی اضافه └── .claude/ ├── rules/ ← قوانین محدود به مسیر (تولیدشده) └── ctx/ ├── INVENTORY.md ← چی تو کد دیدیم ├── DECISIONS.md ← ★ منبع حقیقت — فقط این رو دستی ویرایش کن └── VERIFY.md ← کدوم قانون واقعاً کار کرد

مهم‌ترین قانون کل این سیستم: فقط DECISIONS.md رو دستی ویرایش کن. CLAUDE.md و .claude/rules/* تولید می‌شن و دفعه بعد بازنویسی می‌شن.

03

ابزارها

مربع‌های رنگی بالای هر کارت می‌گن کدوم اندازه پروژه بهش نیاز داره.

/start 123

دو-سه سؤال می‌پرسه، اندازه پروژه رو تعیین می‌کنه، فقط چیزی که لازمه رو راه می‌اندازه.

کِی: یک بار، اول هر پروژه

/next 123

وضعیت پروژه رو می‌خونه و یک کار پیشنهاد می‌ده. اگه پروژه سالمه، می‌گه «هیچی — برو فیچر بعدی».

کِی: هر وقت گیج شدی

/spec-import 123

یه سند brain-dump (ورد / markdown / متن پیست‌شده) رو بین فایل‌های specs/ پخش می‌کنه. جای خالی رو حدس نمی‌زنه — فهرست شکاف‌ها می‌ده.

کِی: سند محصول از قبل داری، قبل از پر کردن دستی specs

/brief 123

توضیح شلخته‌ت رو تبدیل می‌کنه به بریف دقیق: ورودی، خروجی، خارج از دامنه، و شرط تمام شدن.

کِی: قبل از هر کد جدید

/edges 123

قبل از کد لیست می‌کنه چی می‌تونه خراب بشه. انتظار داشته باش اکثرشون IGNORE بشن — این عمدیه.

کِی: بعد از بریف، قبل از کد

/plan-check 123

پلن رو در برابر بریف و قوانین سادگی داوری می‌کنه: scope creep، ساختار حدسی، dependency اضافه. خروجی: GO / TRIM / RETHINK.

کِی: بعد از plan mode، قبل از کد · حتماً تو سشن تازه

/fix-one 123

دقیقاً یک باگ از گزارش: اول تست شکست‌خورده، بعد اصلاح ریشه، چک دامنه، کامیت، تیک.

کِی: بعد از ممیزی · یک مورد در هر جلسه

/ctx-audit 123

کد رو می‌خونه و نقاط تصمیم رو پیدا می‌کنه: سه تا دیت‌پیکر، دو جور فرمت قیمت. قضاوت نمی‌کنه.

کِی: قدم اول پروژه بزرگ موجود

/ctx-interview 123

ازت سؤال چندگزینه‌ای می‌پرسه و تصمیم‌هات رو تو DECISIONS.md ثبت می‌کنه.

کِی: بعد از ctx-audit · ۱۵ دقیقه که کل ارزش سیستم توشه

/ctx-generate 123

از تصمیم‌های تو، CLAUDE.md و فایل‌های قانون می‌سازه. با بودجه سخت‌گیرانه.

کِی: بعد از مصاحبه، و هر بار DECISIONS عوض شد

/ctx-verify 123

تست می‌کنه قوانین واقعاً رفتار رو عوض کردن یا نه. می‌گه کدوم خط رو می‌تونی همین الان پاک کنی.

کِی: بعد از هر تولید · این قدم رو رد نکن

/ctx-learn 123

اصلاحاتی که تو سشن کردی رو استخراج می‌کنه و قانون پیشنهاد می‌ده. سیستم از اشتباه واقعی یاد می‌گیره.

کِی: آخر سشن‌های جدی

/audit-codebase 123

پنج پاس جدا: باگ درستی، منطق اشتباه، کد مرده، انحراف از کانونشن، امنیت. چیزی رو تغییر نمی‌ده.

کِی: روی یک ماژول، نه کل پروژه یکجا

/lazy 123

شدت نردبان سادگی: lite · full · ultra · off. سطح رو توی CLAUDE.md می‌نویسه، پس بین سشن‌ها می‌مونه.

کِی: وقتی حس کردی داره زیادی می‌سازه — یا زیادی کم

/debt 123

مارکرهای lazy: رو جمع می‌کنه توی DEBT.md و چک می‌کنه شرط ارتقای هرکدوم فعال شده یا نه.

کِی: هر چند اسپرینت · قبل از هر جهش ترافیک

/find-overengineering 123

اول می‌شماره بعد قضاوت می‌کنه. برای هر مورد دلیل نگه داشتنش رو هم می‌نویسه.

کِی: وقتی حس کردی کد داره باد می‌کنه

برای اسکریپت یه‌بارمصرف همین سه‌تا کافیه. نه فایل قانون، نه ممیزی، نه موتور context. اگه بعد از دو هفته دیگه بهش دست نمی‌زنی، بیشتر از این لازم نداری — و اضافه کردنش فقط وقتت رو می‌گیره.

04

نقشه راه استفاده

از صفر تا نگهداری، چهار فاز. هیچ فازی رو زودتر از موعدش شروع نکن — پریدن تو فاز ۳ و ۴ دقیقاً همون over-engineeringیه که این جعبه‌ابزار براش ساخته شده.

فازچیابزارکِی
۰ نصبیک بار برای همیشهbash install.shهمین الان
۱ شروعتعیین اندازه و راه‌اندازی حداقلی/startیک بار برای هر پروژه
۲ چرخه فیچرقلب سیستم — بریف تا کامیت/brief → /edges* → plan mode → /plan-check* → کد → تست → /code-reviewهمیشه، هر فیچر
۳ ممیزیپیدا کردن باگ و پیچیدگی اضافه/audit-codebase → /find-overengineering → /fix-one × nTier 2+ · هر چند هفته یا قبل ریلیز
۴ موتور contextقوانین زنده پروژهctx-audit → interview → generate → verify · نگهداری با /ctx-learnفقط Tier 3

* فقط وقتی لازمه: /edges برای کارِ با لبه واقعی، /plan-check برای پلن غیربدیهی. گم شدی؟ همیشه /next.

چرخه فاز ۲ — هر فیچر

/brief← /edges← plan mode← /clear + /plan-check← پیاده‌سازی + تست← /code-review← کامیت← /clear
قانون عبورمحرک
ورود به فاز ۳اولین باگِ برگشتی، یا تحویل گرفتن کدی که خودت ننوشتی. نه زودتر.
ورود به فاز ۴خودت تصمیم نگیر — /next وقتی از آستانه رد شدی (~۶۰ فایل یا نفر دوم) می‌گه.
برگشت به عقبهمیشه مجازه. پروژه Tier 3 هم برای فیکس دو خطی فقط فاز ۲ رو می‌ره.

چهار لحظه هر کار

هر کاری — اپ عظیم یا اسکریپت پنجاه خطی — از چهار لحظه رد می‌شه.

لحظهسؤالابزار
۱. قبل از شروعچی می‌سازیم؟/brief
۲. قبل از کدچطور بنویسیم؟/edges · plan mode · /plan-check · ctx-*
۳. حین ساختثابت کن کار می‌کنه/verify · تست · /code-review
۴. بعد از ساختچی خرابه، چی اضافه‌ست/audit-codebase · /fix-one

05

گزارش‌ها

هر ابزار یه فایل می‌سازه. اینا رو تو گیت بذار.

فایلکی می‌سازتشباهاش چیکار کنم
PROJECT.md/startمرجع. /next می‌خونتش.
BRIEF.md/briefقبل از کد بخون. بعد آرشیوش کن.
INVENTORY.md/ctx-auditورودی مصاحبه. یه بار می‌خونیش.
DECISIONS.md ★/ctx-interviewمنبع حقیقت. فقط این رو ویرایش کن.
VERIFY.md/ctx-verifyREDUNDANTها رو پاک کن، IGNOREها رو درست کن.
AUDIT.md/audit-codebaseچک‌لیست زنده. /fix-one تیک می‌زنه.
COMPLEXITY.md/find-overengineeringهمون. KEEPها رو دست نزن.
DEBT.md/debtهمون. بخش Waiting رو دست نزن — هنوز درسته.

فرمت واحد findingها

AUDIT.md و COMPLEXITY.md هر مورد قابل‌اقدام رو دقیقاً به این شکل می‌نویسن — یه قرارداده، نه سلیقه:

- [ ] #3 BUG src/checkout/total.ts:41 — جمع سبد قبل از اعمال تخفیف گرد می‌شود

/next همین چک‌باکس‌ها رو می‌شماره و /fix-one بعد از اصلاح تیک می‌زنه (- [x] + هش کامیت). موردهای KEEP و سؤال‌های باز چک‌باکس نمی‌گیرن — چیزی برای انجام دادن ندارن.

از کجا شروع کنم؟ نردبان اولویت

۱ شکسته
الان کاربر ضرر می‌کنهداده گم می‌شه · رخنه امنیتی · خطای دیده‌شده
۲ تله
کار می‌کنه ولی تغییر بعدی رو خراب می‌کنهیه منطق تو دو جا · مرز نامشخص
۳ کندکننده
هر فیچر جدید رو کند می‌کنهسه تا دکمه مختلف · بی‌نظمی
۴ زشتی
فقط اذیتت می‌کنهنام‌گذاری · ترتیب

قانون سخت: تا پله ۱ و ۲ خالی نشدن، سراغ ۳ نرو. حتی اگه ۳ آسون‌تره — مخصوصاً وقتی آسون‌تره و حس بهتری می‌ده.

نمی‌دونی از کجا؟ /next بزن. خودش می‌گه کدوم و چرا.

06

آپدیت و ارتقا

سیستم باید با پروژه رشد کنه، نه اینکه کهنه بشه.

الف) قوانین پروژه

DECISIONS.md را ویرایش کن← /ctx-generate← /ctx-verify

هیچ‌وقت CLAUDE.md یا .claude/rules/* رو دستی ویرایش نکن — تولیدشده‌ن و دفعه بعد پاک می‌شن. برای همینه که بالاشون نوشته GENERATED — do not hand-edit.

سه محرک واقعی

کِیچیکار

قوانین طلایی

اگه فقط اینا رو یادت بمونه، ۹۰ درصد فایده رو گرفتی.

01به Claude راهی بده که کارش رو تأیید کنه. تست، بیلد، اسکرین‌شات. بدون چک قابل‌اجرا، «تمام شد» فقط یه حدسه — و تو می‌شی حلقه تأیید.
02/clear بین کارهای نامرتبط. کیفیت با پر شدن context افت می‌کنه.
03بعد از دو اصلاح ناموفق، /clear بزن. سشن تمیز با پرامپت بهتر تقریباً همیشه از سشن طولانیِ پر از اصلاح بهتره.
04هر جلسه اصلاح = یک مورد. نه دو تا.
05پیش‌فرض رو پایین بگیر. بین دو اندازه موندی؟ کوچیک‌تره.
06معیار هر خط قانون: «اگه این رو حذف کنم، Claude اشتباه می‌کنه؟» اگه نه، پاکش کن.
07سه فایل مرجع بهتر از بیست خط توصیفه. مدل از مثال بهتر یاد می‌گیره تا از توصیف.
08هیچ ابزاری نساز تا وقتی دردش رو سه بار حس نکردی.
09پلن رو تو همون سشنی که ساختی قضاوت نکن. /clear بزن، بعد /plan-check. سشنی که پلن رو نوشته وکیل پلنه، نه قاضیش.
