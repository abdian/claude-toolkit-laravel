# آموزش قدم‌به‌قدم — از صفرِ صفر

این فایل با `README.md` فرق داره: اون **مرجعه** (چی هست، کجاست)، این **آموزشه**
(دقیقاً چی تایپ کن، چی می‌بینی، چرا). اگه اولین باره، از همین‌جا شروع کن —
فرض ما اینه که هیچی نمی‌دونی.

قول این فایل: تا آخرش سه تا پروژه واقعی رو قدم‌به‌قدم دیدی، می‌دونی تو هر
موقعیتی چی بزنی، و اشتباهاتی که همه اولش می‌کنن رو نمی‌کنی.

<a id="فصل-۰"></a>
## فصل ۰ — پنج مفهوم به زبان آدمیزاد

قبل از هر دستوری، این پنج تا رو بفهم. بقیه‌ش خودش جا می‌افته.

**۱. Claude Code یه همکار باهوشِ تازه‌واردـه — با حافظه کوتاه‌مدت.**
خیلی خوب کد می‌زنه، ولی هر جلسه (session) که تموم شه، همه‌چی یادش می‌ره.
فردا که برمی‌گردی، دوباره «تازه‌وارد»ـه. کل این جعبه‌ابزار برای حل همینه:
چیزهای مهم رو **توی فایل** نگه می‌داریم، نه توی حافظه‌ی جلسه.

**۲. Context یعنی تخته وایت‌برد جلسه.**
هرچی تو جلسه گفتین و دیدین، روی این تخته‌ست. تخته که پر شه، Claude گیج
می‌زنه — چیزای مهم لای شلوغی گم می‌شن. دستور `/clear` یعنی «تخته رو پاک
کن، جلسه‌ی نو». قانون ساده: **کار عوض شد؟ تخته رو پاک کن.**

**۳. Skill (دستور اسلشی) یعنی برگه دستورالعمل.**
وقتی می‌زنی `/brief`، یه فایل متنی به اسم `SKILL.md` به Claude داده می‌شه
که می‌گه «الان این‌طوری رفتار کن». همین. جادویی در کار نیست — برای همینم
می‌تونی بازشون کنی، بخونی، و عوضشون کنی.

**۴. CLAUDE.md یعنی دفترچه قوانین شرکت.**
اول هر جلسه، Claude این فایل رو می‌خونه. هر قانونی که می‌خوای *همیشه*
رعایت شه (مثلاً «بدون اجازه کامیت نزن») باید این‌جا باشه، نه توی چت —
چون چت پاک می‌شه، فایل می‌مونه.

**۵. گزارش‌ها یعنی لیستِ چسبیده به یخچال.**
ابزارهای ممیزی چیزی رو *درست نمی‌کنن* — فقط یه چک‌لیست می‌سازن
(`AUDIT.md`، `COMPLEXITY.md`). بعداً، تو جلسه‌های جدا، یکی‌یکی تیک می‌خورن.
پیدا کردن و درست کردن دو تا کار جدان — قاطی‌شون نکن.

## فصل ۱ — نصب، پنج دقیقه

```bash
cd claude-toolkit
bash install.sh
```

خروجی باید این شکلی باشه:

```
→ installing to /home/you/.claude/skills  (mode: copy)

  ✓ start
  ✓ next
  ✓ brief
  ✓ plan-check
  ✓ fix-one

done. installed: 5 skill(s)
```

حالا برو تو یه پوشه پروژه (هر پوشه‌ای)، بزن `claude`، و داخلش تایپ کن:

```
/skills
```

اگه پنج تا دستور رو دیدی → تمومه. اگه ندیدی → یه بار از Claude Code خارج
شو و دوباره بازش کن (پوشه‌ی تازه‌ساخته‌شده یه ری‌استارت لازم داره).

**همین الان دو کار دیگه هم بکن** (اختیاری ولی جدی پیشنهاد می‌شه):

۱. محتوای `templates/settings.json.template` رو کپی کن تو
`~/.claude/settings.json` → از این به بعد هیچ کامیتی بدون تأیید تو زده
نمی‌شه و هیچ اسمی از Claude تو کامیت‌ها نمیاد.

۲. بقیه ابزارها رو فعلاً نصب **نکن**. جدی می‌گیم. `--all` رو نگه دار برای
وقتی که فصل ۴ رو لازم داشتی.

<a id="فصل-۲"></a>
## فصل ۲ — اولین پروژه: یه اسکریپت (Tier 1)

**سناریو:** یه فایل `urls.txt` داری با لینک چند تا محصول. می‌خوای
قیمت‌هاشون رو بگیری بریزی تو `prices.csv`. کل ماجرا: ~۲۰ دقیقه.

### قدم ۱ — پوشه و شروع

```bash
mkdir price-scraper && cd price-scraper && git init && claude
```

```
تو:  /start
```

Claude چند تا سؤال چندگزینه‌ای می‌پرسه (با دکمه، نه تایپ):

```
❓ این چیه؟           → [ اسکریپت / جاب داده ]
❓ چقدر عمر داره؟      → [ یه‌بارمصرف — جوابم رو می‌گیرم و تمام ]

▶ THIS IS: اسکریپت، Tier 1
  Set up: هیچی — این پروژه به CLAUDE.md و قانون و ممیزی نیاز نداره
▶ DO THIS NOW: /brief
```

**نکته‌ای که تازه‌کارها رد می‌شن:** جواب «هیچی لازم نیست» یه جواب *درسته*،
نه کم‌کاری. سیستم داره جلوی خودِ تو رو می‌گیره که برای یه اسکریپت،
بوروکراسی نسازی.

### قدم ۲ — بریف

```
تو:  /brief
     یه اسکریپت پایتون می‌خوام که از هر لینک توی urls.txt قیمت محصول رو
     در بیاره و بریزه تو prices.csv
```

Claude فقط سؤال‌هایی می‌پرسه که جوابشون **کد رو عوض می‌کنه**:

```
❓ اگه یه لینک باز نشد (۴۰۴ یا تایم‌اوت) چی؟
   → [ ردش کن، تو ستون error بنویس چرا ]
❓ قیمت با تومان و ویرگوله («۲٬۴۵۰٬۰۰۰ تومان»). خام ذخیره شه یا عدد تمیز؟
   → [ عدد تمیز: 2450000 ]
```

و `BRIEF.md` رو می‌سازه. بازش کن — باید این شکلی باشه:

```markdown
# price-scraper

**Goal** — از لینک‌های urls.txt قیمت بگیر تا بشه هفتگی تغییرات رو دید.

**Inputs**
- urls.txt: هر خط یک URL — مثال: `https://example-shop.ir/p/123`

**Outputs**
- prices.csv: ستون‌های url, price, error — مثال: `https://…/123,2450000,`

**Behaviour**
- قیمت «۲٬۴۵۰٬۰۰۰ تومان» → عدد 2450000 (ارقام فارسی هم تبدیل شن)
- لینک خراب → ردیف با price خالی و error پر، اسکریپت ادامه بده
- بین هر درخواست ۱ ثانیه صبر کن

**Out of scope**
- زمان‌بندی خودکار، دیتابیس، نمودار — هیچ‌کدوم

**Done means**
- `python scrape.py` روی sample_urls.txt (۳ لینک) اجرا شه و csv با ۳ ردیف
  درست بده — یکیش عمداً لینک خراب
```

**دو خطی که کل ارزش این فایلن:** «Out of scope» (جلوی «بذار یه داشبوردم
بزنم» رو می‌گیره) و «Done means» (بدون یه چک قابل‌اجرا، «تمام شد» فقط
حدسه — و *تو* می‌شی تست‌کننده دستی).

### قدم ۳ — بساز و تحویل بگیر

```
تو:  BRIEF.md رو پیاده کن. بعد طبق «Done means» با sample_urls.txt اجرا
     کن و خروجی csv رو نشونم بده.
```

Claude کد رو می‌زنه، اجرا می‌کنه، و خروجی واقعی رو نشون می‌ده. اگه ردیف
خراب error درست داشت → تمومه.

```
تو:  کامیت بزن
تو:  /clear
```

(اگه settings رو تنظیم کرده باشی، قبل از کامیت یه تأییدیه ازت می‌گیره —
همون قانون «کامیت هرموقع من گفتم».)

**تمام.** نه CLAUDE.md ساختی، نه قانون، نه ممیزی — و دقیقاً همین درسته.

## فصل ۳ — پروژه متوسط: اپ ثبت هزینه (Tier 2)

**سناریو:** یه وب‌اپ کوچیک می‌خوای: هزینه‌های روزانه رو ثبت کنی، لیست
ببینی، جمع کل ماه رو ببینی. چند هفته‌ای باهاشی. این‌جا دیگه همه ابزارهای
پایه وارد بازی می‌شن — **مخصوصاً `plan-check`، که ستاره این فصله.**

### قدم ۱ — شروع

```
تو:  /start
❓ این چیه؟        → [ وب‌اپ ]
❓ چقدر عمر داره؟   → [ چند هفته ]
❓ بدترین اتفاق؟    → [ اینکه مبلغ‌ها اشتباه جمع بشن ]

▶ THIS IS: وب‌اپ، Tier 2
  Set up: CLAUDE.md (۱۴ خط) + PROJECT.md
  First milestone: فرم ثبت + لیست + جمع — همین سه تا، سرِ پا و قابل اجرا
▶ DO THIS NOW: /brief
```

`CLAUDE.md` که ساخته رو باز کن — فقط دستورها، یه گوچا، و یه خط قرمز:

```markdown
## Commands
npm run dev / npm test / npx tsc --noEmit

## Gotchas
- مبالغ همیشه به ریال و integer — هیچ‌وقت float

## The one thing
- جمع‌ها هرگز نباید غلط باشن. هر تغییری تو محاسبه → تست الزامی.
```

توجه کن چی *توش نیست*: بخش معماری، بخش استایل، فلسفه. اونا مال Tier 3ان.

### قدم ۲ — بریف و لبه‌ها

```
تو:  /brief
     صفحه ثبت هزینه: مبلغ + دسته + تاریخ. پایینش لیست همین ماه و جمع کل.
```

بعدش:

```
تو:  /edges "فرم ثبت هزینه"
```

خروجی نمونه:

```markdown
| # | Case                         | Severity     | Verdict |
|---|------------------------------|--------------|---------|
| 1 | مبلغ با ارقام فارسی «۲۵۰۰۰»  | wrong result | HANDLE  |
| 2 | مبلغ صفر یا منفی             | wrong result | HANDLE  |
| 3 | مبلغ با ویرگول «25,000»      | wrong result | HANDLE  |
| 4 | تاریخ آینده                  | cosmetic     | IGNORE  |
| 5 | دو تب همزمان باز             | —            | IGNORE  |
| 6 | ۱۰ هزار رکورد                | —            | IGNORE  |

Handle: 3 · Ignore: 9
خطرناک‌ترینِ لیست: ارقام فارسی — چون تست دستی با کیبورد انگلیسی هیچ‌وقت
نمی‌گیردش.
```

**درس این خروجی:** ۹ تا IGNORE یعنی سیستم داره درست کار می‌کنه. کد دفاعی
برای «دو تب همزمان» تو اپ تک‌نفره، خودش over-engineeringـه. IGNORE با
دلیل = یه تصمیم آگاهانه که ثبت شده.

### قدم ۳ — پلن و داوری پلن (مهم‌ترین عادتی که باید بسازی)

```
تو:  [Shift+Tab دوبار → وارد plan mode]
     BRIEF.md رو بخون و برای پیاده‌سازی نقشه بکش.
```

Claude یه پلن می‌ده. فرض کن این رو داد (نمونه واقع‌گرایانه):

```
1. راه‌اندازی state management با یک store سراسری
2. تعریف interface به اسم StorageProvider با پیاده‌سازی LocalStorage
   (که بعداً بشه دیتابیس هم وصل کرد)
3. سیستم دسته‌بندی با فایل config جدا و امکان دسته‌ی تودرتو
4. کامپوننت فرم + اعتبارسنجی
5. کامپوننت لیست + جمع ماهانه
6. دکمه خروجی اکسل
```

قشنگ به نظر میاد، نه؟ **کپیش کن** و:

```
تو:  /clear
تو:  /plan-check
     [پلن رو پیست کن]
```

خروجی:

```
▶ VERDICT: TRIM — شکل کلی درسته، این سه تا رو حذف کن:

1. StorageProvider (قدم ۲) — انتزاع با یک پیاده‌سازی. بریف هیچ حرفی از
   دیتابیس نزده. localStorage مستقیم، ۵ خط.
2. دسته تودرتو + فایل config (قدم ۳) — بریف گفته «دسته». یه آرایه ثابت
   ۶تایی کفایت می‌کنه.
3. خروجی اکسل (قدم ۶) — تو بریف نیست. scope creep کلاسیک.

قدم‌های ۱، ۴، ۵ به بریف وصلن — نگهشون دار.
جاافتاده: با ارقام فارسی تو فیلد مبلغ چیکار می‌کنی؟ (edges شماره ۱)
```

**این لحظه، کل فلسفه‌ی جعبه‌ابزار تو یه قابه:** سه تا چیز «منطقی» که
هیچ‌کس نخواسته بود، *قبل از نوشته شدن حتی یک خط کد* حذف شدن. اگه این
داوری رو تو همون سشن پلن می‌کردی، جواب می‌گرفتی «پلن خوبیه» — چون اون
سشن وکیل پلنشه، نه قاضیش.

### قدم ۴ — بساز، بازبینی کن، ببند

```
تو:  [تو همین سشن تمیز]
     پلن اصلاح‌شده رو پیاده کن. برای تبدیل ارقام فارسی و جمع ماهانه تست
     بنویس. بعد npm test و tsc رو اجرا کن و خروجی رو نشون بده.

     [سبز شد؟]
تو:  /code-review
تو:  کامیت بزن
تو:  /clear
```

فیچر بعدی؟ برگرد به قدم ۲ — همین چرخه. حلقه‌ای که باید ملکه ذهنت شه:

**brief ← edges ← پلن ← clear + plan-check ← کد + تست ← review ← کامیت ← clear**

<a id="فصل-۴"></a>
## فصل ۴ — پروژه بزرگ یا موجود (Tier 3)

**سناریو:** یه اپ ۸ ماهه رو تحویل گرفتی (یا اپ خودت بزرگ شده). کد شلوغه،
Claude «هر بار یه جور» می‌زنه. اول بقیه ابزارها رو نصب کن:

```bash
cd claude-toolkit && bash install.sh --all
```

این فصل سه هفته‌ست، ولی هر هفته فقط چند ساعت.

### هفته ۱ — قانون‌ها رو از توی کد در بیار

```
تو:  /start          → Tier 3 تشخیص می‌ده
تو:  /ctx-audit
```

`ctx-audit` کد رو می‌گرده و «نقاط تصمیم» رو لیست می‌کنه — جاهایی که یه کار
به دو روش انجام شده. نمونه‌ای از `INVENTORY.md`:

```markdown
### Date picker
| Path                    | Approach   | Call sites |
|-------------------------|-----------|-----------:|
| ui/DatePicker.tsx       | جلالی، خودمون |       31 |
| legacy/OldDate.tsx      | میلادی، کتابخونه |    4 |
**Ambiguity:** کدوم استاندارده؟ اون ۴ تا باید مهاجرت کنن یا دلیلی دارن؟
```

توجه: **قضاوت نکرده** — نگفته کدوم درسته. چون نمی‌دونه. تو می‌دونی:

```
تو:  /clear
تو:  /ctx-interview
```

سؤال‌ها این شکلی‌ان (چندگزینه‌ای، ~۱۵ دقیقه):

```
❓ دیت‌پیکر استاندارد کدومه؟
   → [ ui/DatePicker.tsx — اون ۴ تا legacy ان، دست نزن فقط، مهاجرتم نکن ]
❓ چی هست که اگه تو PR ببینی عصبانی شی؟
   → [ any تو تایپ‌اسکریپت. و fetch مستقیم — همه‌چی از api/client بره ]
❓ Claude معمولاً چی رو اشتباه می‌زنه که خودت درستش می‌کنی؟
   → [ برای هر چیزی مودال جدید می‌سازه، در حالی که ui/Modal داریم ]
```

جواب‌هات می‌شه `DECISIONS.md` — **تنها فایلی که دستی ویرایش می‌کنی.** بعد:

```
تو:  /ctx-generate      → CLAUDE.md + .claude/rules/ رو از تصمیم‌هات می‌سازه
تو:  /clear
تو:  /ctx-verify
```

`ctx-verify` جالب‌ترین قدمه: با دو ایجنتِ تازه — یکی با قانون‌ها، یکی بدون —
یه تسک واقعی رو تست می‌کنه و مقایسه می‌کنه:

```markdown
| قانون                  | نتیجه     | اقدام                    |
|------------------------|-----------|--------------------------|
| از ui/Modal استفاده کن | WORKING   | نگه دار                  |
| ارورها رو swallow نکن  | REDUNDANT | پاک کن — بدونشم درست بود |
| فرمت قیمت از helper    | IGNORED   | glob بی‌کوتیشن بود، لود نمی‌شد |
```

**REDUNDANT یعنی پاک کن، نه «چه خوب».** قانونی که بدون وجودش هم رعایت
می‌شه، فقط جا اشغال می‌کنه و بقیه قانون‌ها رو کم‌اثر می‌کنه.

### هفته ۲ — پیدا کن (هیچی رو درست نکن)

```
تو:  /audit-codebase src/features/checkout
تو:  /clear
تو:  /find-overengineering src/features/checkout
```

خروجی اولی، `AUDIT.md` — دقت کن به فرمت چک‌باکسی:

```markdown
## CRITICAL
- [ ] #1 CRITICAL src/checkout/total.ts:41 — تخفیف بعد از گرد کردن اعمال
      می‌شود؛ جمع نهایی تا ۹۹ ریال خطا دارد
      why: پول کاربر · fix: ترتیب round و discount جابه‌جا شود

## BUG
- [ ] #2 BUG src/checkout/form.tsx:88 — ارقام فارسی در کدپستی رد می‌شوند
```

دومی، `COMPLEXITY.md`، برای هر مورد **دفاعیه هم می‌نویسه**:

```markdown
- [ ] #1 REMOVE src/checkout/PaymentFactory.ts:1 — فکتوری با یک درگاه
  Case FOR keeping: «قراره درگاه دوم بیاد» — از ۸ ماه پیش قراره.
  Verdict: REMOVE

(KEEP) src/checkout/retry.ts — پیچیده ولی موجه: تایم‌اوت درگاه واقعیه
```

**تا این‌جا حتی یک خط کد عوض نشده.** فقط دو تا چک‌لیست داری. این جداسازی
عمدیه — پیدا کردن با ذهنِ شکاک، درست کردن با ذهنِ متمرکز.

### هفته ۳ — درست کن، دونه‌دونه

```
تو:  /next
▶ NEXT: /fix-one AUDIT.md 1
  Why: تنها موردیه که الان پول کاربر رو می‌خوره

تو:  /clear
تو:  /fix-one AUDIT.md 1
```

و `fix-one` این مراحل رو *به ترتیب و جلوی چشمت* می‌ره:

```
1. تست شکست‌خورده نوشتم:  total.test.ts → FAIL (expected 24500, got 24599) ✓
2. علت ریشه: round قبل از discount اجرا می‌شه
3. کوچیک‌ترین تغییر: جابه‌جایی دو خط
4. تست‌ها: 14 passed ✓ · tsc ✓
5. git diff --stat → فقط total.ts و total.test.ts ✓
6. نقطه خوبیه برای کامیت — بزنم؟
تو:  کامیت بزن
7. تیک زدم: - [x] #1 … — fixed in a1b2c3d
```

```
تو:  /clear
تو:  /fix-one AUDIT.md 2
```

**یک مورد در هر جلسه. همیشه.** وسوسه‌ی «این سه تا شبیه همن، با هم بزن» رو
بکش — اگه چیزی بشکنه، دیگه نمی‌دونی کدوم شکستش.

و آخرِ هر سشنِ جدی:

```
تو:  /ctx-learn
```

هر جا مجبور شدی Claude رو اصلاح کنی، پیشنهادِ قانون می‌ده که بذاری تو
`DECISIONS.md`. سیستم این‌طوری از اشتباه‌های *واقعی* یاد می‌گیره، نه حدس.

## فصل ۵ — روزمره: «الان چی بزنم؟»

| موقعیت | بزن |
|---|---|
| نمی‌دونم از کجا شروع کنم / برگشتم بعد یه هفته | `/next` |
| سند محصول دارم و `specs/` خالیه | `/spec-import <سند>` ← بعد فقط شکاف‌ها رو مصاحبه کن |
| فیچر جدید می‌خوام | `/brief` |
| پلنِ غیربدیهی دارم | کپی → `/clear` → `/plan-check` |
| کد کار نمی‌کنه، نمی‌دونم چرا | فرضیه بخواه: «۳ فرضیه بده، برای هر کدوم یه آزمایش، از محتمل‌ترین شروع کن» |
| دوبار اصلاحش کردم، بدتر شد | `/clear` + پرامپت بهتر از اول. جدی. |
| حس می‌کنم کد باد کرده | `/find-overengineering src/` |
| یه چیزی مشکوکه ولی مطمئن نیستم | `/audit-codebase <همون ماژول>` |
| باز همون اشتباه همیشگی رو کرد | آخر سشن `/ctx-learn`، بعد `DECISIONS.md` |
| نمی‌دونم قانون‌هام لود شدن یا نه | `/memory` — و اگه شک داری اثر دارن: `/ctx-verify` |
| کارم تموم شد | «کامیت بزن» → `/clear` |

<a id="فصل-۶"></a>
## فصل ۶ — هشت اشتباه رایج

**۱. اجرای کل سیستم روی یه اسکریپت ۱۰۰ خطی.**
علامت: برای مبدل CSV ات `ctx-interview` زدی. درمان: به Tier ای که `/start`
گفت اعتماد کن. شک داشتی؟ پایین‌تره.

**۲. بریف ننوشتن چون «خودم می‌دونم چی می‌خوام».**
بعد نصفه‌ی کار می‌گی «نه، منظورم این نبود» — و اون دوباره‌کاری، ده برابرِ
دو دقیقه‌ی بریفه. مخصوصاً «Done means» — بدون اون، *تو* تست‌کننده‌ی دستیِ
هر تغییری.

**۳. داوری پلن تو همون سشنی که پلن رو ساخته.**
جواب همیشه «پلن خوبیه» درمیاد. بی‌فایده‌ست. کپی → `/clear` → `/plan-check`.

**۴. چند تا فیکس تو یه جلسه.**
جلسه سوم، تستی قرمز می‌شه که نمی‌دونی کدوم تغییر قرمزش کرد. یک جلسه = یک
مورد = یک کامیت = قابل برگشت.

**۵. CLAUDE.md رو کردن انبارِ آرزوها.**
«کد تمیز بنویس»، «بهترین شیوه‌ها را رعایت کن» — این‌ها هیچ رفتاری رو عوض
نمی‌کنن، فقط قانون‌های واقعی رو لای خودشون خفه می‌کنن. تستِ هر خط: «حذفش
کنم، اشتباه می‌کنه؟» نه → حذف.

**۶. تیک نزدن گزارش‌ها.**
موردی که فیکس شده ولی `- [ ]` مونده، ماه بعد دوباره «فیکس» می‌شه.
(`fix-one` خودش تیک می‌زنه — دستی فیکس کردی؟ دستی هم تیک بزن.)

**۷. ویرایش دستی فایل تولیدشده.**
`CLAUDE.md` تولیدشده رو دستی عوض کردی → دفعه بعدِ `ctx-generate` پرید.
مسیر همیشه: `DECISIONS.md` → `/ctx-generate`.

**۸. ادامه دادن به سشنِ خراب.**
دو بار اصلاح کردی و هنوز غلطه؟ سشن آلوده‌ست — رویکردهای شکست‌خورده تو
context ان و مدل بهشون برمی‌گرده. `/clear` + یه پرامپت بهتر تقریباً همیشه
از ادامه دادن جلوتره.

<a id="فصل-۷"></a>
## فصل ۷ — سؤالات پرتکرار

**همه ۱۶ تا رو باید بلد باشم؟**
نه. ۹۰٪ روزت این پنج‌تاست: `brief` → `plan-check` → «کامیت بزن» → `next` →
`fix-one`. بقیه ابزارِ موقعیت‌های خاصن.

**فرق `/brief` با plan mode چیه؟**
بریف می‌گه **چی** می‌خوایم (قرارداد، به زبون تو). پلن می‌گه **چطوری**
بسازیمش (نقشه فنی). اول چی، بعد چطوری — و `plan-check` داورِ «چطوری»ست
در برابر «چی».

**فرق `/plan-check` با `/find-overengineering`؟**
یه چیز رو دو جا می‌گیرن: اولی **قبل از کد** (روی پلن — ارزون)، دومی
**بعد از کد** (روی کدی که از دستت در رفته). اگه اولی رو جدی بگیری، دومی
کم‌کار می‌شه.

**فرق `/audit-codebase` با `/code-review`؟**
`/code-review` (مالِ خود Claude Code) فقط تغییرات اخیر رو می‌بینه — بعد از
هر فیچر. `/audit-codebase` کل یه ماژول رو عمیق می‌گرده — هر چند هفته یا
قبل ریلیز.

**وسط یه پروژه‌ی موجودم — می‌تونم الان شروع کنم؟**
آره، اتفاقاً بهترین جاست. `/start` وضع موجود رو می‌سنجه و اگه Tier 3 بود
می‌فرستدت سراغ `ctx-audit` — مسیر فصل ۴ دقیقاً برای همینه.

**چند وقت یه بار ممیزی بزنم؟**
با تقویم نه، با محرک: باگِ برگشتی دیدی، کدِ غریبه تحویل گرفتی، یا قبل
ریلیز. `/next` هم اگه لازم باشه خودش می‌گه.

**`ctx-verify` گرون نیست؟**
چرا — چند ایجنت اجرا می‌کنه. برای همین فقط Tier 3، فقط بعد از تولید یا
تغییر قانون‌ها. هر روز نمی‌زنیش.

**این با OpenSpec / spec-kit چه نسبتی داره؟**
مکمل، نه رقیب. اون‌ها لایه‌ی proposal و اسپکِ تغییراتن؛ این جعبه‌ابزار
لایه‌ی *رفتار روزمره* و ضد-over-engineering. پروژه/تیم که بزرگ‌تر شد،
می‌تونی `brief` رو با proposal های OpenSpec عوض کنی — بقیه ابزارها سر
جاشون می‌مونن.

**از کجا بفهمم داره جواب می‌ده؟**
سه علامت بعد از دو هفته: (۱) کمتر می‌گی «نه، منظورم این نبود»، (۲)
گزارش‌های ممیزی کوتاه‌ترن، (۳) دیگه کدی که «برای آینده» نوشته شده تو
ریپوت پیدا نمی‌شه.
