`v1.7-laravel` · ۱۷ ابزار · استارتر `specs/` · تمپلیت لاراول

> 🎓 **اولین باره؟** این فایل *مرجعه*. آموزش قدم‌به‌قدم با دیالوگ واقعی،

> و نسخه تعاملی HTML اش: **[`tutorial.html`](tutorial.html)** (دیالوگ‌های حبابی، خروجی‌های
> تاشو، FAQ بازشو). از یکی از این دو شروع کن، سه پروژه کامل رو باهم می‌ریم.

## ۱. ایده اصلی در یک دقیقه

مشکل این نیست که Claude بد کد می‌زنه. مشکل اینه که **راهی نداره بفهمه کارش درست بوده یا نه**، و **نمی‌دونه تو این پروژه کارها چطوری انجام می‌شن**.

این جعبه‌ابزار سه‌تا چیز رو حل می‌کنه:

| مشکل | راه‌حل |
|---|---|
| «هر بار یه جور می‌زنه» | فایل‌های قانون که کانونشن‌های پروژه رو نگه می‌دارن |
| «نمی‌فهمم کارش درست بوده یا نه» | هر کاری با یه چک قابل‌اجرا تموم می‌شه |
| «پیدا می‌کنم ولی درست نمی‌شه» | حلقه اصلاح تکی با تست |

و یه اصل که همه‌جا تکرار می‌شه:

> **پیش‌فرض رو پایین بگیر.** بیشتر کارها به هیچی از این‌ها احتیاج ندارن.

## ۲. نصب

پوشه `claude-toolkit/` رو بذار **داخل** پروژه‌ات (اسمش رو `_toolkit` بذاری
هم فرقی نمی‌کنه) و از داخلش نصب کن.

### نصب سریع (پیشنهادی)

```bash
cd _toolkit          # یا claude-toolkit — هرجا که گذاشتیش
bash install.sh
```

این **شش ابزار پایه** رو نصب می‌کنه: `start`، `next`، `brief`، `plan-check`،
`fix-one`، `lazy`. با همین‌ها شروع کن. بقیه رو وقتی لازم شدن اضافه کن.

### همه ابزارها

```bash
bash install.sh --all        # هر ۱۷ تا
```

### پروژه‌ای یا سراسری؟

پیش‌فرض **پروژه‌ای** است: ابزارها می‌رن تو `.claude/skills/` همون پروژه و فقط
همون‌جا کار می‌کنن. این یعنی می‌تونی کامیتشون کنی و هم‌تیمی‌هات هم داشته
باشنشون، و یعنی هر پروژه می‌تونه نسخه خودش رو داشته باشه.

```bash
bash install.sh --all --global    # به‌جاش تو ~/.claude/skills/
```

> ⚠️ **یک skill شخصی، skill پروژه‌ای هم‌نام رو کنار می‌زنه.** اگه قبلاً
> سراسری نصب کرده بودی، نصب پروژه‌ای هیچ اثری نداره و هنوز نسخه قدیمی اجرا
> می‌شه. یا سراسری رو پاک کن، یا با `--global` سراسری رو به‌روز کن.

### symlink یا کپی

پیش‌فرض **symlink** است: یک نسخه روی دیسک، و ویرایش `skills/` فوراً همه‌جا
اعمال می‌شه. جایی که symlink واقعی ممکن نباشه (ویندوز بدون Developer Mode)
اسکریپت **کپی واقعی نصب می‌کنه و صریحاً بهت می‌گه** — در اون حالت بعد از هر
ویرایش باید `--force` بزنی.

```bash
bash install.sh --all --copy     # کپی واقعی، عمداً
bash install.sh --all --force    # چیزی که هست رو بازنویسی کن
```

بدون `--force` هر چیزی که از قبل نصب باشه دست‌نخورده می‌مونه — پس اجرای
دوباره اسکریپت بی‌خطره.

### بررسی نصب

داخل Claude Code:

```
/skills        ← باید لیست ابزارها رو نشون بده
/doctor        ← اگه چیزی پیدا نشد، دلیلش رو می‌گه
```

> **نکته:** skill پروژه‌ای از پوشه‌ای لود می‌شه که `claude` رو **از داخلش**
> اجرا کردی (و از `.claude/skills` زیرش) — نه از پوشه‌های بالاتر. اگه چیزی
> نیومد، اول چک کن `claude` رو از ریشه پروژه اجرا کرده باشی.
>
> برای نصب **سراسری**، اگه `~/.claude/skills` تازه ساخته شده یک بار Claude
> Code رو ری‌استارت کن. بعد از اون ویرایش‌ها بدون ری‌استارت اعمال می‌شن.

> **ویندوز:** `install.sh` رو از Git Bash یا WSL اجرا کن، نه cmd/PowerShell.

### همراهان اختیاری — که عمداً داخل این بسته نیستن

اگه روی لاراول کار می‌کنی، دو تا زنجیره‌ابزار بیرونی هست که کنار این جعبه‌ابزار
خوب می‌شینن. **هیچ‌کدوم اینجا کپی نشدن و نباید بشن** — هر دو skillهاشون رو
خودشون تولید و به‌روز می‌کنن، و یه کپی منجمد از اون‌ها فقط بعد از اولین
`composer update` دروغ می‌شه.

| ابزار | نصب | چی اضافه می‌کنه |
|---|---|---|
| **Laravel Boost** | `composer require laravel/boost --dev` | `laravel-best-practices`، `infer-conventions`، `tailwindcss-development` + سرور MCP با `search-docs` و `record-rule` |
| **OpenSpec** | `npm i -g openspec` سپس `openspec init` | `openspec-propose`، `openspec-apply-change`، `openspec-explore`، `openspec-sync-specs`، `openspec-archive-change` |

تقسیم کار ساده‌ست و همپوشانی ندارن:

- **این جعبه‌ابزار** → «چی بسازم و چقدر ساده نگهش دارم» (`specs/`، `/brief`،
  `/plan-check`، `/lazy`، `/debt`)
- **OpenSpec** → «این تغییر مشخص رو چطور مرحله‌به‌مرحله ببرم جلو»
- **Boost** → «لاراول رو درست بنویس» + داکیومنت نسخه‌دقیق

> skillهای Boost بدون سرور MCP لاراول نیمه‌کاره‌ان (به `search-docs` تکیه
> می‌کنن). `.mcp.json` پروژه باید `laravel-boost` رو داشته باشه:
> ```json
> { "mcpServers": { "laravel-boost": { "command": "php", "args": ["artisan","boost:mcp"] } } }
> ```

### قانون کامیت (اختیاری، پیشنهادی)

دو لایه — طبق قانون خود سیستم: چیزهای «هیچ‌وقت/همیشه» فقط قانون نباشن،
اجرای قطعی هم داشته باشن.

**لایه ۱ — قانون:** (پروژه لاراولی؟ از `templates/CLAUDE.laravel.md.template`
شروع کن — همین ساختار، ولی با دستورات artisan/Pest/Pint و قوانین مایگریشن و
پیش‌فرض MariaDB/Redis.) تمپلیت `templates/CLAUDE.md.template` حالا بخش
`Git — commit policy` داره: کامیت فقط با دستور صریح تو (تموم شدن تسک اجازه
نیست)، استثنا برای skillهایی که کامیت جزو قراردادشونه (`/fix-one`)، و
هیچ اسمی از Claude/AI هیچ‌جای کامیت — نه footer، نه `Co-Authored-By:`، نه
توی بدنه پیام. اگه می‌خوای این قانون روی *همه* پروژه‌هات باشه بدون اینکه تو
هر CLAUDE.md تکرارش کنی، بذارش تو `~/.claude/CLAUDE.md` — سراسری لود می‌شه.

**لایه ۲ — اجرا:** محتوای `templates/settings.json.template` رو کپی کن تو
`~/.claude/settings.json` (سراسری) یا `.claude/settings.json` پروژه:

```json
{
  "attribution": { "commit": "", "pr": "" },
  "permissions": { "ask": ["Bash(git commit:*)"] }
}
```

- `attribution` با رشته خالی، خط `Co-Authored-By` و footer «Generated with
  Claude Code» رو به‌صورت قطعی حذف می‌کنه.
- `permissions.ask` یعنی هر `git commit` قبل از اجرا ازت تأیید می‌گیره —
  «هرموقع گفتم» به معنای واقعی، حتی اگه مدل قانون رو گم کنه.

> ⚠️ اگه جایی `includeCoAuthoredBy` دیدی: از نسخه 2.0.62 منسوخ شده. با
> `attribution` همزمان استفاده‌ش نکن — تداخل می‌کنن. فقط `attribution`.
> ضمناً `attribution` فقط بخشِ خودکارِ ته پیام رو برمی‌داره، نه بدنه‌ای که
> مدل می‌نویسه — برای همین لایه ۱ همچنان لازمه، و برعکس. با هم کامل‌ان.

## ۳. نقشه فایل‌ها — چی کجا می‌ره

### الف) ابزارها — پیش‌فرض داخل پروژه

```
my-project/
├── _toolkit/                      ← خود جعبه‌ابزار، تو گیت پروژه
│   ├── install.sh
│   ├── docx2md.py                 ← مبدل docx→md برای /spec-import
│   ├── skills/                    ← منبع اصلی، اینجا ویرایشش می‌کنی
│   └── templates/
└── .claude/skills/                ← install.sh اینجا لینک/کپی می‌کنه
    ├── start/SKILL.md                 ← در ورودی
    ├── next/SKILL.md                  ← راننده روزمره
    ├── brief/SKILL.md                 ← چی می‌سازیم
    ├── edges/SKILL.md                 ← حالت‌های مرزی
    ├── plan-check/SKILL.md            ← داور پلن، قبل از کد
    ├── fix-one/SKILL.md               ← اصلاح تکی
    ├── lazy/SKILL.md                  ← شدت سخت‌گیری نردبان
    ├── debt/SKILL.md                  ← دفتر میان‌برهای عمدی
    ├── spec-import/                   ← پخش سند brain-dump در specs/
    │   ├── SKILL.md
    │   └── docx2md.py                 ← همراه skill سفر می‌کنه
    ├── ctx-audit/SKILL.md             ┐
    ├── ctx-interview/SKILL.md         │
    ├── ctx-generate/SKILL.md          ├─ موتور context (فقط پروژه بزرگ)
    ├── ctx-verify/SKILL.md            │
    ├── ctx-learn/SKILL.md             ┘
    ├── audit-codebase/SKILL.md        ┐
    └── find-overengineering/SKILL.md  ┘─ ممیزی (فقط پروژه بزرگ)
```

با `--global` همین درخت `skills/` به‌جای `.claude/skills/` پروژه، تو
`~/.claude/skills/` می‌شینه و تو همه پروژه‌ها در دسترسه. `~` یعنی پوشه خونه:
`/home/نام-کاربری/` در لینوکس و مک، `C:\Users\نام-کاربری\` در ویندوز.

**اسم پوشه = اسم دستور.** پوشه `fix-one` ⟵ دستور `/fix-one`.

### ب) خروجی‌ها — داخل هر پروژه، تو گیت

```
my-project/
├── PROJECT.md              ← وضعیت پروژه. /start می‌سازتش.
├── BRIEF.md                ← چی داریم می‌سازیم. /brief می‌سازتش.
├── CLAUDE.md               ← قوانین سراسری پروژه. تولیدشده یا دستی.
├── AUDIT.md                ← لیست باگ‌ها. چک‌لیست زنده.
├── COMPLEXITY.md           ← لیست پیچیدگی‌های اضافه.
├── DEBT.md                 ← میان‌برهای عمدی (مارکر lazy:). /debt می‌سازتش.
└── .claude/
    ├── rules/              ← قوانین محدود به مسیر (تولیدشده)
    │   ├── components.md
    │   └── api.md
    ├── skills/             ← ابزارهای مخصوص همین پروژه (اختیاری)
    └── ctx/
        ├── INVENTORY.md    ← چی تو کد دیدیم
        ├── DECISIONS.md    ← ⭐ منبع حقیقت — این رو دستی ویرایش کن
        └── VERIFY.md       ← کدوم قانون واقعاً کار کرد
```

> ⚠️ **مهم‌ترین قانون کل این سیستم:**
> فقط `DECISIONS.md` رو دستی ویرایش کن. `CLAUDE.md` و `.claude/rules/*`
> تولید می‌شن و دفعه بعد بازنویسی می‌شن.

### ج) `specs/` — تصمیم‌های محصول، قبل از اولین خط کد

جعبه‌ابزار یه استارتر `specs/` هم همراهشه (پوشه `specs/` کنار
`claude-toolkit/`، یا `specs-starter.zip`). کپیش کن تو ریشه پروژه لاراولت.

```
specs/
├── HOWTO.md          ← ⭐ از اینجا شروع کن — ترتیب پر کردن و پرامپت هر قدم
├── README.md         ← چی اینجا می‌آد، چی نمی‌آد
├── VISION.md         ← ① محصول در یک جمله، کاربرها، MVP، Non-goals
├── GLOSSARY.md       ← ② اسم قطعی هر موجودیت — قبل از هر فایل دیگه
├── PERMISSIONS.md    ← ③ ماتریس «کی به چی دسترسی داره»
├── INTEGRATIONS.md   ← ④ سرویس‌های بیرونی و رفتارشون وقتی بالا نیستن
├── FLOWS.md          ← ⑤ مسیرهای چندمرحله‌ای، با مسیر خطا
├── PANELS.md         ← ⑤ فهرست صفحات هر پنل، با مجوزش
├── ARCHITECTURE.md   ← پیش‌فرض‌ها چیده شده؛ فقط وقتی منحرف شدی دست بزن
├── BACKLOG.md        ← ⑥ فقط عنوان + یک خط. جزئیات فیچر اینجا نمی‌آد.
└── contracts/        ← قرارداد OpenAPI هر سرویس بیرونی
```

**ترتیب اجباریه.** `GLOSSARY.md` قبل از همه‌چیز، چون اسم جدول و مدل ازش
درمی‌آد — و مایگریشنِ merge‌شده فریزه. اسم غلط تا آخر عمر پروژه می‌مونه.

دو تا قرارداد نگارشی که همه‌جای این فایل‌ها تکرار می‌شن:

- `[...]` یعنی **جای خالی، پرش کن.**
- `[؟]` یعنی **هنوز تصمیم گرفته نشده.** تا وقتی `[؟]` سر جاشه، روی اون
  موجودیت کد نوشته نمی‌شه. بخشی که اصلاً لازم نداری رو کلاً پاک کن —
  نگه داشتنِ ماتریسِ یه قابلیتِ ناموجود، ایجنت رو به ساختنش وسوسه می‌کنه.

> سند محصول از قبل داری؟ به‌جای پر کردن دستی، `/spec-import` بزن و بعد فقط
> شکاف‌هایی که گزارش می‌ده رو مصاحبه کن.

## ۴. سه سایز پروژه

بزرگ‌ترین اشتباه ممکن اینه که کل سیستم رو روی یه اسکریپت ۱۰۰ خطی اجرا کنی.

| سایز | چی هست | چی لازم داره |
|---|---|---|
| 🟢 **۱ — سبک** | اسکریپت یه‌بارمصرف، اسکرپر، تبدیل فایل. زیر ~۱۵ فایل. | `/brief` + یک تست واقعی. **همین.** |
| 🟡 **۲ — متوسط** | افزونه، CLI، سرویس کوچیک. چند هفته عمر. ~۱۵ تا ۶۰ فایل. | `/brief` + `CLAUDE.md` کوتاه + `/edges` + `/fix-one` |
| 🔴 **۳ — کامل** | اپلیکیشن، پروژه تیمی، چیزی که ماه‌ها زنده می‌مونه. بالای ~۶۰ فایل. | همه‌چی |

**قاعده:** وقتی بین دو سایز موندی، **پایینی** رو بردار. رفتن به سایز بالاتر
یه دستور هزینه داره؛ برگشتن یعنی پاک کردن فایل‌هایی که خودت رو قانع کردی
لازمن — و کسی این کار رو نمی‌کنه.

`/start` این تصمیم رو خودش می‌گیره. بهش اعتماد کن.

## ۵. هر ابزار چیکار می‌کنه

### 🚪 در ورودی

#### `/start` — یک بار، اول هر پروژه
دو-سه تا سؤال می‌پرسه، سایز پروژه رو تعیین می‌کنه، **فقط چیزی که لازمه** رو
راه می‌اندازه، و `PROJECT.md` می‌نویسه.

```
> /start
❓ این چیه؟        → [ اسکریپت ]
❓ چقدر عمر داره؟  → [ یه‌بارمصرف ]

▶ THIS IS: اسکریپت، Tier 1
  Set up: هیچی — این پروژه نیازی نداره
▶ DO THIS NOW: /brief
```

#### `/next` — هر وقت گیج شدی
وضعیت پروژه رو می‌خونه و **یک کار** پیشنهاد می‌ده. نه لیست، نه نقشه راه.
اگه پروژه سالمه، می‌گه «هیچی — برو فیچر بعدی رو بنویس».

---

### 📝 قبل از کد

#### `/brief` — چی می‌سازیم
توضیح شلخته تو رو تبدیل می‌کنه به `BRIEF.md` با ورودی، خروجی، رفتار،
**خارج از دامنه**، و **شرط تمام شدن**.

```
> /brief
یه اسکریپت می‌خوام از سایت X قیمت بگیره
```

بخش «شرط تمام شدن» مهم‌ترین بخشه. بدون یه چک قابل‌اجرا، «تمام شد» فقط یه حدسه.

#### `/spec-import` — سند شلخته → `specs/`
یک سند brain-dump (`.docx`، `.md`، یا متنی که تو سشن پیست کردی) رو می‌خونه و
محتواش رو بین فایل‌های `specs/` پخش می‌کنه.

```
> /spec-import سند-محصول.docx
```

**مهم‌ترین خروجیش فایل‌هایی نیست که پر می‌کنه، فهرست شکاف‌هاییه که پر
*نکرده*.** قانونش اینه که فقط چیزی رو بنویسه که سند صریحاً گفته؛ هر جای
خالی، خالی می‌مونه و تو گزارش می‌آد. پر کردن جای خالی با یه جواب باورپذیر،
بدترین حالته — هیچ‌وقت متوجه نمی‌شی تصمیمی گرفته نشده، فقط پر شده.

بعدش `/clear` کن و فقط برای شکاف‌های گزارش‌شده مصاحبه کن، نه از اول. سند
کار قدم‌های آسون رو کرده؛ چیزی که مونده همون تصمیم‌های سخته.

> `.docx` با `docx2md.py` تبدیل می‌شه — کتابخونه استاندارد پایتون، بدون
> pandoc و بدون `pip install`. جدول‌ها رو هم درست درمی‌آره، که مهمه چون
> `GLOSSARY` و `PERMISSIONS` و `PANELS` همه جدولن.

#### `/edges` — حالت‌های مرزی
قبل از کد، لیست می‌کنه چی می‌تونه خراب بشه: ورودی خالی، شبکه قطع، تاریخ مرزی،
یونیکد، دو کاربر همزمان.

```
> /edges "فرم ثبت سفارش"
```

**انتظار داشته باش اکثرشون IGNORE بشن.** این عمدیه — کد دفاعی برای حالت‌های
غیرممکن، خودش یه نوع over-engineeringه.

#### `/plan-check` — ⭐ داور پلن
ارزون‌ترین جای گرفتن over-engineering مرحله پلنه، نه بعد از نوشته شدن کد.
این ابزار پلن رو در برابر `BRIEF.md` و قوانین سادگی داوری می‌کنه: قدم‌های
بی‌ریشه (scope creep)، ساختارهای حدسی با یک مصرف‌کننده، dependency های
غیرضروری، و وزن دفاعی اضافه. خروجیش یه verdict ساده‌ست: GO / TRIM / RETHINK.

```
[پلن آماده شد — کپیش کن]
> /clear
> /plan-check
  [پلن رو پیست کن]
▶ VERDICT: TRIM — این ۲ مورد رو حذف کن، بعد شروع کن
```

> **قانونش:** حتماً تو سشن **تازه**. سشنی که پلن رو ساخته، bias های تو و
> خودش رو به ارث برده — وکیل پلنه، نه قاضیش.

### 🔍 بعد از ساخت

#### `/audit-codebase` — باگ‌یابی
پروژه یا یه ماژول رو در پنج پاس بررسی می‌کنه: باگ‌های درستی، منطق اشتباه،
کد مرده، انحراف از کانونشن، مسائل امنیتی. **هیچی رو تغییر نمی‌ده** —
`AUDIT.md` می‌سازه.

```
> /audit-codebase src/features/checkout
```

#### `/find-overengineering` — پیچیدگی اضافه
اول **می‌شماره** بعد **قضاوت می‌کنه**: انتزاع با یک پیاده‌سازی، wrapper بی‌فایده،
گزینه مرده، dependency بی‌مصرف. برای هر مورد **دلیل نگه داشتنش** رو هم می‌نویسه.

```
> /find-overengineering src/
```

#### `/debt` — دفتر میان‌برهای عمدی
هر جا عمداً یه گوشه رو گرد کردی، یه کامنت `lazy:` گذاشتی که سقفش رو می‌گه.
`/debt` همه‌شون رو جمع می‌کنه و — نکته اصلی — **چک می‌کنه شرط ارتقا فعال شده
یا نه**. یه مارکر ۱۸ماهه روی جدولی که هنوز ۴۰ رکورد داره، از یه مارکر
سه‌هفته‌ای روی مسیر پرداخت پایین‌تره.

```php
// lazy: شمارنده in-memory، وقتی روی بیش از یک نود رفت ببرش Redis
```

```
> /debt                → کل ریپو
> /debt app/Services   → یه زیرشاخه
> /clear
> /fix-one DEBT.md 2   → یکی رو تسویه کن (مارکر هم تو همون کامیت پاک می‌شه)
```

خروجی `DEBT.md` با همون فرمت چک‌باکسِ `AUDIT.md`ه، پس `/next` می‌شمارتش و
`/fix-one` تیک می‌زنه.

> **مارکر `lazy:` با `TODO` فرق داره.** TODO یعنی چیزی نیست. `lazy:` یعنی کد
> کار می‌کنه، ولی سقفش اینجاست. قانون «هیچ TODOیی ننویس» سر جاشه.

#### `/lazy` — شدت سخت‌گیری
سطح نردبان رو عوض می‌کنه و **توی خود `CLAUDE.md` می‌نویسه**، پس بین سشن‌ها
می‌مونه (بر خلاف mode‌های in-memory که با هر سشن ریست می‌شن).

```
> /lazy          → سطح فعلی رو می‌گه
> /lazy ultra    → عوضش می‌کنه
```

| سطح | رفتار |
|---|---|
| `lite` | همون چیزی که خواستی رو می‌سازه، بعد در یک خط راه تنبل‌تر رو می‌گه. انتخاب با تو. |
| `full` | نردبان اجرا می‌شه. فریم‌ورک و stdlib قبل از کد سفارشی. **پیش‌فرض.** |
| `ultra` | افراطی. حذف قبل از اضافه. یک‌خطی رو می‌ده و بقیه صورت‌مسئله رو زیر سؤال می‌بره. |
| `off` | نردبان تعطیل. ولی قوانین دامنه، کانونشن و درستی سر جاشونن. |

#### `/fix-one` — ⭐ حلقه اصلاح
**دقیقاً یک مورد** رو از گزارش برمی‌داره: اول تست شکست‌خورده می‌نویسه، بعد
ریشه رو درست می‌کنه، دامنه رو چک می‌کنه، کامیت می‌زنه، تیک می‌زنه تو گزارش.

```
> /clear
> /fix-one AUDIT.md 3
```

> **هر جلسه = یک مورد.** نه دو تا. اگه خراب شد باید بدونی کدوم خرابش کرده.

### 🏗️ موتور context — فقط پروژه بزرگ (Tier 3)

این پنج‌تا با هم یه زنجیره‌ن. **ترتیبشون مهمه.**

| ابزار | کار | خروجی |
|---|---|---|
| `/ctx-audit` | کد رو می‌خونه، نقاط تصمیم رو پیدا می‌کنه. قضاوت نمی‌کنه. | `INVENTORY.md` |
| `/ctx-interview` | ازت سؤال می‌پرسه، تصمیم‌هات رو ثبت می‌کنه | `DECISIONS.md` ⭐ |
| `/ctx-generate` | از تصمیم‌ها، فایل‌های قانون می‌سازه | `CLAUDE.md` + `rules/` |
| `/ctx-verify` | تست می‌کنه رفتار واقعاً عوض شد یا نه | `VERIFY.md` |
| `/ctx-learn` | آخر سشن، از اصلاحات تو قانون پیشنهاد می‌ده | متن |

**چرا این‌طوریه؟**
Claude می‌تونه توصیف کنه چی **هست**، ولی نمی‌تونه بدونه چی **باید** باشه.
اگه بگی «پروژه رو ببین و قوانینم رو بنویس»، بی‌نظمی موجود رو مستند می‌کنه.
پس: اول فهرست‌برداری، بعد **تو** تصمیم می‌گیری، بعد تولید.

## ۶. نقشه راه استفاده — از صفر تا نگهداری

کل سیستم **چهار فازه**. هیچ فازی رو زودتر از موعدش شروع نکن — فاز ۳ و ۴ فقط
مال Tierهای بالاست، و پریدن توشون دقیقاً همون over-engineeringیه که این
جعبه‌ابزار براش ساخته شده.

### نمای کلی

```
فاز ۰ · نصب — یک بار برای همیشه
│   bash install.sh
▼
فاز ۱ · شروع پروژه — یک بار برای هر پروژه
│   /start  →  Tier مشخص می‌شه  →  PROJECT.md (با milestone اول و Non-goals)
▼
فاز ۲ · چرخه هر فیچر — قلب سیستم، همیشه
│
│   /brief ──→ /edges* ──→ plan mode ──→ /clear + /plan-check* ──→ پیاده‌سازی
│      ▲                                                              │
│      │                            کامیت ← /code-review ← تست/verify ┘
│      └─────────────────── /clear → فیچر بعدی ←──────────────────────┘
▼
فاز ۳ · ممیزی دوره‌ای — Tier 2+ ، هر چند هفته یا قبل از ریلیز
│   /audit-codebase → /find-overengineering → [ /clear + /fix-one ] × n
▼
فاز ۴ · موتور context — فقط Tier 3
    راه‌اندازی:  /ctx-audit → /ctx-interview → /ctx-generate → /ctx-verify
    نگهداری:    /ctx-learn آخر سشن‌های جدی · /next خودش staleness رو می‌گیره

*  فقط وقتی لازمه: /edges برای کارِ با سطحِ لبه واقعی، /plan-check برای پلن غیربدیهی
همیشه و همه‌جا: گم شدی؟  /next
```

### کدوم فاز برای کدوم Tier

| فاز | 🟢 Tier 1 | 🟡 Tier 2 | 🔴 Tier 3 |
|---|---|---|---|
| ۱ — شروع | ✓ | ✓ | ✓ |
| ۲ — چرخه فیچر | فقط `/brief` + یک تست | کامل | کامل |
| ۳ — ممیزی | ✗ | قبل از ریلیز | دوره‌ای |
| ۴ — موتور context | ✗ | ✗ | ✓ |

### قانون عبور بین فازها

- **ورود به فاز ۳:** اولین باری که یه باگِ برگشتی دیدی، یا کدی رو تحویل
  گرفتی که خودت ننوشتی. نه زودتر.
- **ورود به فاز ۴:** خودت تصمیم نگیر — `/next` وقتی از آستانه رد شدی
  (~۶۰ فایل، یا نفر دوم کامیت زد) بهت می‌گه.
- **برگشت به عقب همیشه مجازه:** پروژه Tier 3 هم برای یه فیکس دو خطی فقط
  فاز ۲ رو می‌ره — بدون brief هم اگه واقعاً بدیهیه.

## ۷. گزارش‌ها

هر ابزار یه فایل تولید می‌کنه. اینا رو **تو گیت بذار** — تاریخچه تصمیم‌هات هستن.

| فایل | کی می‌سازتش | چی توشه | باهاش چیکار کنم |
|---|---|---|---|
| `PROJECT.md` | `/start` | سایز، فاز، چی استفاده می‌کنیم و چی نه | مرجع. `/next` می‌خونتش. |
| `BRIEF.md` | `/brief` | چی می‌سازیم، شرط تمام شدن | قبل از کد بخون. بعد از تموم شدن آرشیوش کن. |
| `INVENTORY.md` | `/ctx-audit` | چند تا دیت‌پیکر داری، چند جور قیمت | ورودی مصاحبه. یه بار می‌خونیش. |
| `DECISIONS.md` ⭐ | `/ctx-interview` | تصمیم‌های تو | **منبع حقیقت.** فقط این رو ویرایش کن. |
| `VERIFY.md` | `/ctx-verify` | کدوم قانون کار کرد، کدوم نه | REDUNDANTها رو پاک کن. IGNOREها رو درست کن. |
| `AUDIT.md` | `/audit-codebase` | باگ‌ها با شماره و شدت | **چک‌لیست زنده.** `/fix-one` تیک می‌زنه. |
| `COMPLEXITY.md` | `/find-overengineering` | پیچیدگی اضافه + دلیل نگه داشتن | همون. KEEPها رو دست نزن. |
| `DEBT.md` | `/debt` | میان‌برهای عمدی + اینکه شرط ارتقاشون فعال شده یا نه | همون. بخش Waiting رو دست نزن — اون‌ها هنوز درستن. |

### فرمت واحد findingها — یه قرارداد، نه سلیقه

`AUDIT.md` و `COMPLEXITY.md` و `DEBT.md` هر مورد قابل‌اقدام رو دقیقاً به این شکل می‌نویسن:

```markdown
- [ ] #3 BUG src/checkout/total.ts:41 — جمع سبد قبل از اعمال تخفیف گرد می‌شود
```

`/next` همین چک‌باکس‌ها رو می‌شماره، و `/fix-one` بعد از اصلاح تیک می‌زنه
(`- [x]` + هش کامیت آخر خط). موردهای KEEP و سؤال‌های باز چک‌باکس **نمی‌گیرن** —
چیزی برای انجام دادن ندارن و چک‌باکسی که هیچ‌وقت نباید تیک بخوره، شمارنده رو
مسموم می‌کنه.

### چطور گزارش بخونم

**اولویت اجرا** — همیشه این ترتیب:

| پله | یعنی | مثال |
|---|---|---|
| 🔴 **۱. شکسته** | الان کاربر ضرر می‌کنه | داده گم می‌شه، رخنه امنیتی |
| 🟠 **۲. تله** | کار می‌کنه ولی تغییر بعدی رو خراب می‌کنه | یه منطق تو دو جا |
| 🟡 **۳. کندکننده** | هر فیچر جدید رو کند می‌کنه | سه تا دکمه مختلف |
| ⚪ **۴. زشتی** | فقط اذیت می‌کنه | نام‌گذاری |

**قانون سخت:** تا پله ۱ و ۲ خالی نشدن، سراغ ۳ نرو. حتی اگه ۳ آسون‌تره —
مخصوصاً وقتی آسون‌تره.

نمی‌دونی از کجا شروع کنی؟ `/next` بزن. خودش می‌گه.

## ۸. به‌روزرسانی و ارتقا

### الف) به‌روزرسانی قوانین پروژه

```
DECISIONS.md را ویرایش کن  →  /ctx-generate  →  /ctx-verify
```

**هیچ‌وقت `CLAUDE.md` یا `.claude/rules/*` رو دستی ویرایش نکن** — تولیدشده‌ن
و دفعه بعد پاک می‌شن. برای همینه که بالاشون نوشته
`GENERATED — do not hand-edit`.

**سه محرک واقعی:**

| کِی | چیکار |
|---|---|
| آخر سشن‌های جدی | `/ctx-learn` |
| **دو بار پشت سر هم یه اصلاح تکراری کردی** | قانون کهنه شده → `DECISIONS.md` |
| حس کردی داره یه‌جور دیگه می‌زنه | `/ctx-verify` |

اون وسطی مهم‌ترینه. لازم نیست تقویم بذاری — **اصطکاک خودش بهت می‌گه.**

و یه تور ایمنی هم هست: اگه `DECISIONS.md` رو ویرایش کردی و یادت رفت
`/ctx-generate` بزنی، `/next` خودش می‌فهمه (تاریخ فایل‌ها رو مقایسه می‌کنه)
و همون رو پیشنهاد می‌ده. تصمیمی که regenerate نشده، فقط یه یادداشته.

### ب) ارتقای سایز پروژه

پروژه Tier 1 بزرگ شده؟ `/next` خودش وقتی از آستانه رد شدی بهت می‌گه. بخش
`Promote when` تو `PROJECT.md` دقیقاً برای همینه — تصمیم رو **از قبل** گرفتی،
نه تو لحظه‌ای که کلافه‌ای.

```
> /next
▶ NEXT: /ctx-audit
  Why: پروژه از ۶۰ فایل رد شد و دو نفر روش کامیت می‌زنن
```

### ج) به‌روزرسانی خود جعبه‌ابزار

اگه با `--link` نصب کردی:


## ۱۰. قوانین طلایی

1. **به Claude راهی بده که کارش رو تأیید کنه.** تست، بیلد، اسکرین‌شات. بدون
   چک قابل‌اجرا، «تمام شد» فقط یه حدسه — و تو می‌شی حلقه تأیید.

2. **`/clear` بین کارهای نامرتبط.** کیفیت با پر شدن context افت می‌کنه.

3. **بعد از دو اصلاح ناموفق، `/clear` بزن** و از اول با پرامپت بهتر شروع کن.
   سشن تمیز با پرامپت بهتر تقریباً همیشه از سشن طولانیِ پر از اصلاح بهتره.

4. **هر جلسه اصلاح = یک مورد.** نه دو تا.

5. **پیش‌فرض رو پایین بگیر.** بین دو سایز موندی؟ کوچیک‌تره.

6. **معیار هر خط قانون:** «اگه این رو حذف کنم، Claude اشتباه می‌کنه؟» اگه نه،
   پاکش کن. فایل متورم از فایل نداشته بدتره.

7. **سه فایل مرجع بهتر از بیست خط توصیفه.** مدل از مثال بهتر یاد می‌گیره.

8. **هیچ ابزاری نساز تا وقتی دردش رو سه بار حس نکردی.**

9. **پلن رو تو همون سشنی که ساختی قضاوت نکن.** `/clear` بزن، بعد `/plan-check`.
   سشنی که پلن رو نوشته وکیل پلنه، نه قاضیش — و over-engineering ارزون‌ترین
   جای گرفتنش روی کاغذه، نه توی کد.
