۰۰

پنج مفهوم به زبان آدمیزاد

قبل از هر دستوری این پنج تا رو بفهم — بقیه‌ش خودش جا می‌افته.

۱
Claude Code = همکار باهوشِ تازه‌وارد، با حافظه کوتاه‌مدت

خیلی خوب کد می‌زنه، ولی هر جلسه که تموم شه همه‌چی یادش می‌ره. فردا دوباره «تازه‌وارد»ـه. کل این جعبه‌ابزار برای حل همینه: چیزهای مهم رو توی فایل نگه می‌داریم، نه توی حافظه‌ی جلسه.

۲
Context = تخته وایت‌برد جلسه

هرچی تو جلسه گفتین و دیدین روی این تخته‌ست. تخته که پر شه، Claude گیج می‌زنه. /clear یعنی «تخته رو پاک کن، جلسه‌ی نو». قانون ساده: کار عوض شد؟ تخته رو پاک کن.

۳
Skill (دستور اسلشی) = برگه دستورالعمل

وقتی می‌زنی /brief، یه فایل متنی به Claude داده می‌شه که می‌گه «الان این‌طوری رفتار کن». جادویی در کار نیست — برای همینم می‌تونی بازشون کنی، بخونی و عوضشون کنی.

۴
CLAUDE.md = دفترچه قوانین شرکت

اول هر جلسه خونده می‌شه. هر قانونی که می‌خوای همیشه رعایت شه (مثل «بدون اجازه کامیت نزن») باید این‌جا باشه، نه توی چت — چون چت پاک می‌شه، فایل می‌مونه.

۵
گزارش‌ها = لیستِ چسبیده به یخچال

ابزارهای ممیزی چیزی رو درست نمی‌کنن — فقط چک‌لیست می‌سازن (AUDIT.md، COMPLEXITY.md). بعداً تو جلسه‌های جدا، یکی‌یکی تیک می‌خورن. پیدا کردن و درست کردن دو تا کار جدان.

حالا تو یه پوشه پروژه بزن claude و داخلش /skills — پنج تا دستور رو دیدی؟ تمومه. ندیدی؟ یه بار Claude Code رو ببند و باز کن (پوشه‌ی تازه‌ساخته یه ری‌استارت لازم داره).

همین الان دو کار دیگه هم بکن: ۱) محتوای templates/settings.json.template رو کپی کن تو ~/.claude/settings.json — از این به بعد هیچ کامیتی بدون تأیید تو زده نمی‌شه و هیچ اسمی از Claude تو کامیت‌ها نمیاد. ۲) بقیه ابزارها رو فعلاً نصب نکن. جدی می‌گیم — --all رو نگه دار برای وقتی فصل ۴ رو لازم داشتی.

# price-scraper

**Goal** — از لینک‌های urls.txt قیمت بگیر تا بشه هفتگی تغییرات رو دید.

**Inputs**
- urls.txt: هر خط یک URL — مثال: https://example-shop.ir/p/123

**Outputs**
- prices.csv: ستون‌های url, price, error

**Behaviour**
- «۲٬۴۵۰٬۰۰۰ تومان» ← عدد 2450000 (ارقام فارسی هم تبدیل شن)
- لینک خراب ← ردیف با price خالی و error پر، اسکریپت ادامه بده
- بین هر درخواست ۱ ثانیه صبر

**Out of scope**
- زمان‌بندی خودکار، دیتابیس، نمودار — هیچ‌کدوم

**Done means**
- python scrape.py روی sample_urls.txt (۳ لینک، یکیش عمداً خراب)
  اجرا شه و csv با ۳ ردیف درست بده

دو خطی که کل ارزش این فایلن: «Out of scope» (جلوی «بذار یه داشبوردم بزنم» رو می‌گیره) و «Done means» — بدون یه چک قابل‌اجرا، «تمام شد» فقط حدسه و تو می‌شی تست‌کننده دستی.

قدم ۳ — بساز و تحویل بگیر

توBRIEF.md رو پیاده کن. بعد طبق «Done means» با sample_urls.txt اجرا کن و خروجی csv رو نشونم بده.
claudeکد رو نوشتم و اجرا کردم — سه ردیف، ردیف دوم error درست داره: 
url,price,error
https://…/123,2450000,
https://…/bad,,HTTP 404
https://…/456,1890000,
توکامیت بزن
تو/clear

تمام. نه CLAUDE.md ساختی، نه قانون، نه ممیزی — و دقیقاً همین درسته. (اگه settings رو تنظیم کرده باشی، قبل از کامیت یه تأییدیه ازت گرفت — همون قانون «کامیت هرموقع من گفتم».)

داوری پلن تو همون سشنی که پلن رو ساختهجواب همیشه «پلن خوبیه» درمیاد. بی‌فایده‌ست. کپی ← /clear ← /plan-check.
۴
چند تا فیکس تو یه جلسهجلسه سوم، تستی قرمز می‌شه که نمی‌دونی کدوم تغییر قرمزش کرد. یک جلسه = یک مورد = یک کامیت.
۵
CLAUDE.md رو کردن انبارِ آرزوها«کد تمیز بنویس» هیچ رفتاری رو عوض نمی‌کنه، فقط قانون‌های واقعی رو خفه می‌کنه. تستِ هر خط: «حذفش کنم، اشتباه می‌کنه؟» نه ← حذف.
۶
تیک نزدن گزارش‌هاموردی که فیکس شده ولی - [ ] مونده، ماه بعد دوباره «فیکس» می‌شه. fix-one خودش تیک می‌زنه؛ دستی فیکس کردی؟ دستی تیک بزن.
۷
ویرایش دستی فایل تولیدشدهCLAUDE.md تولیدشده رو دستی عوض کردی ← دفعه بعدِ ctx-generate پرید. مسیر همیشه: DECISIONS.md ← /ctx-generate.
۸
ادامه دادن به سشنِ خرابدو بار اصلاح کردی، هنوز غلطه؟ رویکردهای شکست‌خورده تو context ان و مدل بهشون برمی‌گرده. /clear + پرامپت بهتر تقریباً همیشه جلوتره.
۰۷

سؤالات پرتکرار

روی هر سؤال بزن تا باز شه.

▸همه ۱۳ تا رو باید بلد باشم؟

نه. ۹۰٪ روزت این پنج‌تاست: brief ← plan-check ← «کامیت بزن» ← next ← fix-one. بقیه ابزارِ موقعیت‌های خاصن.

▸فرق /brief با plan mode چیه؟

بریف می‌گه چی می‌خوایم (قرارداد، به زبون تو). پلن می‌گه چطوری بسازیمش (نقشه فنی). اول چی، بعد چطوری — و plan-check داورِ «چطوری»ست در برابر «چی».

▸فرق /plan-check با /find-overengineering؟

یه چیز رو دو جا می‌گیرن: اولی قبل از کد (روی پلن — ارزون)، دومی بعد از کد (روی چیزی که از دستت در رفته). اولی رو جدی بگیری، دومی کم‌کار می‌شه.

▸فرق /audit-codebase با /code-review؟

/code-review (مالِ خود Claude Code) فقط تغییرات اخیر رو می‌بینه — بعد از هر فیچر. /audit-codebase کل یه ماژول رو عمیق می‌گرده — هر چند هفته یا قبل ریلیز.

▸وسط یه پروژه‌ی موجودم — می‌تونم الان شروع کنم؟

آره، اتفاقاً بهترین جاست. /start وضع موجود رو می‌سنجه و اگه Tier 3 بود می‌فرستدت سراغ ctx-audit — مسیر فصل ۴ دقیقاً برای همینه.

▸چند وقت یه بار ممیزی بزنم؟

با تقویم نه، با محرک: باگِ برگشتی دیدی، کدِ غریبه تحویل گرفتی، یا قبل ریلیز. /next هم اگه لازم باشه خودش می‌گه.

▸ctx-verify گرون نیست؟

چرا — چند ایجنت اجرا می‌کنه. برای همین فقط Tier 3، فقط بعد از تولید یا تغییر قانون‌ها. هر روز نمی‌زنیش.

▸این با OpenSpec / spec-kit چه نسبتی داره؟

مکمل، نه رقیب. اون‌ها لایه‌ی proposal و اسپکِ تغییراتن؛ این جعبه‌ابزار لایه‌ی رفتار روزمره و ضد-over-engineering. پروژه/تیم بزرگ‌تر شد، می‌تونی brief رو با proposal های OpenSpec عوض کنی — بقیه سر جاشون می‌مونن.

▸از کجا بفهمم داره جواب می‌ده؟

سه علامت بعد از دو هفته: (۱) کمتر می‌گی «نه، منظورم این نبود»، (۲) گزارش‌های ممیزی کوتاه‌ترن، (۳) دیگه کدی که «برای آینده» نوشته شده تو ریپوت پیدا نمی‌شه.

۰۸

برگه تقلب

همه‌ی این صفحه، تو یه قاب.

یه بار برای همیشه   bash install.sh  +  settings.json (قانون کامیت)
یه بار هر پروژه     /start
هر فیچر             /brief → /edges* → plan → /clear + /plan-check* → کد
                    → تست → /code-review → «کامیت بزن» → /clear
گم شدی              /next
هر چند هفته (T2+)   /audit-codebase → /find-overengineering → /debt
هر فیکس             /clear → /fix-one گزارش شماره   ← یکی، فقط یکی
فقط پروژه بزرگ      /ctx-audit → interview → generate → verify
آخر سشن جدی         /ctx-learn
* = فقط وقتی لازمه

سه قانون بالای همه: ۱) کار عوض شد ← /clear   ۲) پلن رو تو سشن خودش قضاوت نکن   ۳) «تمام شد» بدون چک قابل‌اجرا، حدسه.
